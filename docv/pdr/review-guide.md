# ドキュメントを蒸留する手順を docv review-guide で出し、基準は Doc ガイドに置く

## 背景

AI Agent と開発すると、機能やコードはあまり増えないのに、ドキュメントだけが作業の報告のように増えていく。増えるほど、人間がプロジェクトの状態を一瞥できなくなる。

Doc ガイドは、書くときに従う方針である。溜まったドキュメントをまとめてレビューする手順はなかった。

レビューの観点は、ほとんどが Doc ガイドの基準と同じことになる。ミッションに沿っているか、同じことが複数の箇所にないか、ページをどう分けるかなどである。

## 決めたこと

レビューの判断の基準と、見て回る手順を分けて置く。

| 分けたもの                                                                                           | 置き場所                                                                        | 調整できるか                |
| ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | --------------------------- |
| 判断の基準（何が望ましくないか）                                                                     | Doc ガイド                                                                      | プロジェクトで直せる        |
| 手順、観点、削るべきでないもの、判断に使わないもの、直し方、報告の形                                 | `docv review-guide` の出力と、HTML の Review Guide のページ。バイナリに埋め込む | 直せない。docv の版で決まる |
| 一覧（Slot と Free ファイルのパス、ミッション、タグ、打ち消されていない ADR と PDR、`docv_exclude`） | `docv review-guide` が、実行するたびにファイルから作る                          | 書くものではない            |

- レビューの目的は、蒸留にする
  - 今の姿と決まり、その理由、境目（やらないこと）を残し、それ以外を除く
  - それらを読み取りやすくする概要や例、参照も残す
  - 量を減らすことは目的にしない
- review-guide は指摘を出さない
  - ファイルを読んで確かめ、指摘するのは、出力を受け取った AI Agent である
- 一覧には、読んでも分からないことか、AI Agent が自分で集めると間違えやすいことだけを出す
- 一覧に見出しは出さない
  - 対象はすべて読ませるので、同じことを 2 度読ませることになるため
- 一覧に行数は出さない
  - 数が並ぶと、大きいものを悪いと受け取るため
- 手順と Doc ガイドが食い違うときは、Doc ガイドに従う
  - 基準をプロジェクトで調整できるようにするため
- Doc ガイドにあって観点にない基準も、レビューで確かめる
  - プロジェクトが足した基準も効かせるため
- レビューの対象は、Slot と Free ファイルにする
  - ADR と PDR は対象にしない
- 一覧には、打ち消されていない ADR と PDR を出す
  - Slot や Free ファイルにある経緯が、決定にも書いてあるかを確かめるのに使う
  - 今の姿として書いたことが、決定と食い違っていないかを確かめるのにも使う
  - 打ち消された決定は、履歴なので出さない
- ファイルどうしの矛盾は、どちらが今の姿かを調べて直す
  - 分からなければ、人間に確かめる
- 決定との矛盾は揃えず、人間に確かめる
  - 決定を変えるには、新しい ADR か PDR が要るため
- レビューの結果はファイルに書かず、直すのは人間が選んでからにする
  - レビューの報告が、新しい作業の報告として溜まらないようにするため
- 観点ごとに直し方を決め、AI Agent はその中から選ぶ
  - 決めていないと、AI Agent は自分の好みで直し方を決め、書き足す直し方を選びがちなため
- ドキュメントのどこにも書いていない情報は、書き足さない
  - 例外は、決定との矛盾で新しい ADR か PDR を書くことだけ
- 指摘に添える直し方は、どれを選んでもドキュメントが変わるものだけにする
  - 人間が断った指摘を、次のレビューで繰り返さないため
- 人間が「このままでいい」と答えた指摘は、その判断を一般化した 1 行を、Doc ガイドに足す案として示す
  - Doc ガイドが例外の一覧になって観点が効かなくならないよう、観点を丸ごと外す 1 行にはしない
  - その箇所だけの例外は、次のレビューでも指摘されるのを受け入れる
- 削るべきでないものと判断に使わないものを、観点と並べて出す
  - 量を減らすよう頼まれた AI Agent は、決まりの理由や境目まで削ったり、大きさで判断したりするため
- Doc ガイドの雛形に、レビューの基準になることを足す
  - 作業の報告、冗長、折りたたみ、箇条書き、図、概要、ページをまとめること、メモの片付け
  - ADR と PDR を書いたら、作成基準に照らして見直すという指示
- `docv build` が作る HTML のサイドバーに Review Guide のページを置き、review-guide と同じ手順を出す
  - レビューするときに AI Agent が読むものを、人間も普段から同じ観点で読めるようにするため
  - サイドバーにあれば、レビューのコマンドがあることも忘れにくいため
- HTML のページには、一覧を出さない
  - build した時点の一覧がずれていき、HTML を git で管理していると、Slot や ADR を足すたびに差分が出るため
- review-guide の使い方は、`docv desc` と利用マニュアルに書く
- Doc ガイドの雛形には、手順は書かず、レビューを提案するきっかけだけを書く
  - きっかけは、作業中に 2 つ以上のファイルで望ましくない記述を見つけたときと、リリースの前や大きな機能を入れた後
  - いつレビューするかは、プロジェクトで調整したいことなので、ガイドラインに当たる

## 結果

- AI Agent に「`docv review-guide` に従ってレビューして」と頼めば、どのプロジェクトでも同じ手順でレビューできる
- 人間は、HTML の Review Guide のページで、AI Agent と同じ観点を読める
- プロジェクトは、Doc ガイドを直すことで、レビューの基準を足したり緩めたりできる
  - 観点そのものは調整できない
- 断った指摘は、ドキュメントが変わるので、次のレビューでは出ない
  - その箇所だけの例外として残したものは、レビューのたびに指摘される
- 書くときにすり抜けた、ふさわしくない ADR と PDR は、レビューでは見つからない
  - 増えて読みにくくなるのは ADR と PDR の系譜の図で、今の状態を一瞥することは崩れない
- すでに Doc ガイドを作ったプロジェクトには、雛形に足した基準が入らない
  - Doc ガイドは、docv の版を上げても書き換えないため
  - 版を上げるときに、update-guide で足した基準を案内する

## 見直す条件

- review-guide の出力を書き写し、観点を直したファイルをプロジェクトに置く利用者が出たとき
  - 観点もプロジェクトで調整したいという合図になる
- ADR と PDR に、作成基準の書かないものに当たる記録が溜まっているのを見つけたとき
  - ADR と PDR をレビューの対象から外したことを見直す

## 選ばなかった案

| 案                                                             | 選ばなかった理由                                                                                                      |
| -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| レビューガイドの Slot を作り、雛形を生成してプロジェクトで直す | 基準が Doc ガイドと 2 か所になり、ずれていく。Slot はプロジェクトの状態を書く場所で、レビューの手順はそれに当たらない |
| Doc ガイドの雛形に、レビューの手順を書く                       | たまにしか使わない手順を、毎回のセッションで読ませることになる                                                        |
| 観点ごとの基準も、コマンドに埋め込む                           | プロジェクトで基準を調整できない。プロジェクトで直した Doc ガイドとずれる                                             |
| docv が LLM を呼んで、指摘まで出す                             | docv は、AI Agent に渡す文を出すところまでにしている                                                                  |
| ドキュメントを減らすこと（圧縮）を目的にする                   | 量を目的にすると、決まりの理由や境目まで削られ、大きさで判断するようになる                                            |
| ページの行数などに上限を決めて指摘する                         | ドキュメントの絶対的な大きさに正解はない。分けるかどうかは中身で決める                                                |
| ADR と PDR もレビューの対象にする                              | 今の姿ではなく、書き換えない記録である。ふさわしいかは、書くときに決めたほうが早い                                    |
| ADR と PDR を書いた直後用のコマンドを分ける                    | 基準は Doc ガイドにあり、書くときに読まれている。1 件ずつ確かめるので、docv が作る一覧も要らない                      |
| ADR と PDR をすべて一覧に出す                                  | 打ち消された決定を今の決定として読み、誤った食い違いを指摘させてしまう                                                |
| 決まった間隔でレビューを促す                                   | docv は状態を持たず、前回いつレビューしたかを知らない                                                                 |
| ドキュメントの量でレビューを促す                               | ドキュメントの大きさに正解はない                                                                                      |
| check でレビューを促す                                         | check は意味を判断しない                                                                                              |
| 断った指摘を、ファイルに記録して次から除く                     | レビューの記録が、新しい作業の報告として溜まる。docv が状態を持つことにもなる                                         |
| 本文に「指摘しない」印（`<!-- keep -->` など）を付ける         | 人間が読むドキュメントに雑音が入る。AI Agent が、指摘を黙らせるために印を付けるようになる                             |
| 前回のレビューから変わったファイルだけを見る                   | docv は前回のレビューを知らない。古くからある問題を見逃す                                                             |
| 句点で文を重ねた箇条書きを check で指摘する                    | 徹底させるのに手間がかかる。AI Agent がよく書く形なので、なくそうとすると、かえって手間が増える                       |
