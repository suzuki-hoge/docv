# システム仕様

## 処理の流れ

1. カレントディレクトリをルートにし、そこにある `docv.yaml` を読む。親のディレクトリは探さない
2. `docv.yaml` を読んでスキーマで確かめ、ルート以下のファイルを分類する
3. コマンドに応じて、検査、出力、書き換えのどれかに進む

結果は標準出力に、エラーは標準エラーに出す。

## ファイルを書くコマンド

| コマンド | 書くもの                                                                                                                                                                                                                           |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| init     | `docv.yaml` だけ。`--print` のときは書かない                                                                                                                                                                                       |
| slot gen | 指定した Slot ファイルだけ。`--print` のときは書かない                                                                                                                                                                             |
| fix      | 管理対象のファイル、`dir.slot` の中の Markdown（md の Slot と ADR）、YAML の Slot だけ。整形と textlint の自動修正だけをする。YAML の Slot は、Markdown の項目の中身だけを直す。`docv.yaml` と YAML の Slot は、末尾の改行も整える |
| build    | `dir.html` と `dir.image` の中だけ。目印の `.docv` を残して中を消し、作り直す。`--no-image` のときは `dir.image` に触れない                                                                                                        |

- ほかのコマンドは、ファイルを書かない
- `CLAUDE.md`、リポジトリのルートの `.gitignore`、hook の設定は、どのコマンドも書かない
- build は、出力先に `.docv`（docv が作った目印）がなく、空でもないときは、何も書かずにエラーで終わる。`dir.html` や `dir.image` を間違えて既存のディレクトリを指しても消さないため

## ファイルの分類

| 分類     | 条件                                                                                     |
| -------- | ---------------------------------------------------------------------------------------- |
| 除外     | `.gitignore` に書かれている、`dir.html` か `dir.image` の中にある、`ignore` に当てはまる |
| 管理対象 | `dir.free` のディレクトリの下の Markdown                                                 |
| 管理外   | それ以外の Markdown。中身は見ない                                                        |

Slot は、Markdown とは別に、`dir.slot`（既定は `docv/`）から `<まとまり>/<ID>.<拡張子>` の名前のファイルだけを読む。拡張子は Slot ごとに決まる（YAML か md）。ページに分けたサービス仕様は、`service/service/` の直下の md を 1 ページずつ読む。知らない項目があれば、読めない Slot として check が error にする。

`dir.slot` の中でも、除外に当たるファイルと、名前がドットで始まるファイルとディレクトリ（`.DS_Store` など）は読まない。それ以外で Slot の名前でないファイルは、check が slot-unknown の error にする。

`dir.free`、`dir.slot`、`dir.html`、`dir.image`（書いたとき）は、どの 2 つも同じディレクトリにも、一方が他方を含む関係にもできない。`docv.yaml` を読むときに確かめ、違反していれば、どのコマンドもファイルを読み書きせずに終了コード 2 で終わる。

`dir.slot` の中の Markdown（md の Slot と ADR）には、Free ファイルの YAML front matter のルールのほかは、管理対象のファイルと同じ検査をかける。YAML の Slot は、`_markdown` で終わる項目の中身を Markdown として読み、同じく検査する。`docv check` にパスを渡したときも、検査するファイルが絞られるだけで、かける検査は変わらない。

## バイナリに埋め込むもの

Rust で書いた単一のバイナリにし、次のものを埋め込む。利用者に Rust の環境はいらない。

- Slot のテンプレ（`assets/template/`。YAML の Slot の項目のサンプルと、ドキュメントのガイドラインの雛形）
- YAML の Slot と `docv.yaml` のスキーマ（`assets/schema/`）
- docv の概要（`docv desc` が出す `assets/desc.md`。`docv/service/service.md` はこのファイルへのシンボリックリンク）
- HTML の CSS（`assets/style.css`）
- 検索のページの JS（`assets/search.js`）
- Markdown の整形に使う dprint-plugin-markdown
- コードブロックの色付けに使う syntect と、その構文の定義とテーマ

textlint を使うときだけ Node.js が、JPG を作るときだけ Chrome が要る。`docv.yaml` と YAML の Slot の JSON Schema（`assets/schema/`）は、埋め込むほかにリポジトリでも公開する。`docv init` と `docv slot gen` は、ファイルの 1 行目に、版のタグを含む URL を書いて参照させる。

## HTML の作り

- CSS は各ページの中に書く。外部の CDN は使わない。file:// で開いても、そのままホスティングしても見られる
- JS は、決定のページのカーソルキーでの移動、プロジェクト詳細のタグのトグル、検索のページにだけ使い、ページの中に書く。どれも JPG にしないページで、JS が動かなくても、すべての中身は読め、リンクから辿れる。OS ごとの手順のタブは、JS を使わず CSS で切り替える。分けたサービス仕様のタブは、ページへのリンクにする
- すべてのページの左に、トップの 5 ページ（プロジェクト概要、ADR、プロジェクト詳細、現在の設定、検索）へのサイドバーを、右に、そのページの h2 と h3 の目次を置く。見出しのないページでは、目次の代わりに同じ幅の空きを置き、ページを移っても本文の位置を変えない。印刷の表示（JPG）では、どちらのサイドバーも出さない
- 検索のページは、Slot ファイル、ADR、Free ファイルの中身を行ごとに並べた索引を、ページの中に書く。入力した文字列をそのまま含む行を探し、入力欄の下に、ファイルごとにパス、タグ、ヒットした行の前後 2 行を並べる。プレビューの長い行は、折り返さずに横へスクロールする。入力欄は、JS が動くときだけ出す
- フェンスのコードブロックは、フェンスに書いた言語（`yaml` など）に合わせて、build のときに色を付ける。色は HTML の中に埋め込み、JS は使わない。言語がないか、syntect が知らない言語なら、色を付けずに出す
- リンクは、Free ファイル、Slot ファイル、ADR のページにだけ、出力先の中の相対パスで張る（ツリー、Slot ファイルや Free ファイルの本文の中のリンク）。file:// で開けば file:// のまま、ホスティングすればその中で辿れる。`docv.yaml` へのリンクは、現在の設定のページに向ける。HTML は clone したリポジトリで見るので、ほかのファイル（コード、管理外のファイルなど）はエディタで開けばよく、リンクにせず文字だけを出す
- 本文の中の http:// と https:// で始まる URL は、`[文字](URL)` の形で書いていなくてもリンクにする。URL は、空白、`<`、`>`、ASCII でない文字の前で終わり、末尾の句読点と、対になっていない `)` は含めない。日本語の文と続けて書いても、後ろの文を URL に含めないため。リンク、画像、コードの中の URL は変えない
- 画像は、元のファイルを出力先から辿れる相対パスで読む
- 表のセルの中のインラインコードは、折り返さない。コマンドやパスが途中で切れないようにするため

## 毎回同じ出力にする決まり

- 生成日時、実行したマシンのパス、乱数を出力に入れない
- 並び順を固定する。Slot は規格の順（分けたサービス仕様のページは `order` とパスの順）、Free ファイルはディレクトリのツリーの順、Slot の中の項目は書いた順、ADR は日付と id の順。検索の索引は、Slot ファイル、ADR、Free ファイルの順
- 入力（管理対象のファイル、Slot、ADR、`docv.yaml`、docv の版）が同じなら、HTML はバイト単位で同じになる
- JPG は、同じマシン・同じ Chrome・同じフォントなら同じになる。違うマシンで同じにすることはしない。チームで JPG を共有するなら、GitHub Actions などの決まった環境で作る

## JPG の撮り方

`dir.image` を書いたときだけ、build の最後に撮る。`--no-image` を付けると撮らない。撮った JPG は、`dir.image` に `<まとまり>/<Slot>.jpg` の名前で置く。ローカルの Chrome をヘッドレスで起動し、DevTools Protocol で出力先の HTML を開いて撮る。幅は 1280 CSS ピクセル、画質は 80。印刷の表示にし、ページの高さに画面を合わせて、Slot のページを 1 枚ずつ撮る。Chrome は、環境変数 DOCV_CHROME、OS ごとの標準のインストール先、PATH にある chrome と chromium の順に探し、見つからなければ error で終わる。

## 終了コード

| コード | 意味                                                                                         |
| ------ | -------------------------------------------------------------------------------------------- |
| 0      | 成功。check で指摘が 1 件もない                                                              |
| 1      | check で指摘（error）が 1 件以上ある。fix で直せないファイルがある。open に対応していない OS |
| 2      | `docv.yaml` がスキーマに合わない、引数が正しくない、など実行できない                         |

## 言語

CLI のメッセージ、ヘルプ、docv の概要、テンプレは、日本語だけで書く。切り替えはできない。英語に訳した版を持つと、同じことを 2 か所で揃え続けることになるため。
