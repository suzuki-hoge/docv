# サービス仕様

プロジェクトのドキュメントを、AI Agent が読み書きする Markdown（原本）と、人間が全体像を掴む HTML の 2 つの形で扱うためのフレームワーク。ルールと、そのルールを前提にした CLI からなる。

- 原本は、ファイルごとに答えること（mission）を宣言した Markdown。docs/ に、プロジェクトが自由に書く。AI Agent は mission を見て、必要なファイルだけを読む
- どのプロジェクトにもある問い（インストール、サービス仕様、利用マニュアルなど）は、docv の規格のファイル（枠）として docv/ に、決まった形で書く
- 人間向けの HTML は、枠ごとのページと、それらへのカードを並べた index.html（プロジェクト概要）。折りたたまないので、画像にしても読める
- ファイルの分類は、任意の数を付けられるタグで行う。タグにルール（過去の言い回しを書かない、など）を付けられる
- HTML とインデックスは、LLM を使わずに作る。同じ入力からは毎回同じものができる。すべてローカルで完結する

## 解決すること

- ドキュメントが無秩序に書き足され、全体像がつかめない
- 初めて訪れた人や久しぶりに触った人が、「これは何か」「どう入れて、どう動かすか」「どこに何があるか」にすぐ答えられない
- そのたびに AI Agent が全部読んでまとめると、時間とトークンがかかり、結果も毎回変わる

Markdown のファイルを増やすだけでは、どれだけ整理しても全体像は見えてこない。docv は、ドキュメントのルールと、そのルールを前提にした CLI を 1 つのフレームワークとして提供する。

## 原本と、人間向けの情報

原本と人間向けの情報は、粒度が違う。

|          | 原本（Markdown）                 | 人間向けの情報（HTML）                                         |
| -------- | -------------------------------- | -------------------------------------------------------------- |
| 読む人   | AI Agent。詳細の記録として人間も | 初めて訪れた人、全体像を掴みたい人                             |
| 単位     | 1 つの問いに答えるファイル       | どのプロジェクトにもある問い（インストール、サービス仕様など） |
| 粒度     | 細かい。理由、境界、例外まで書く | 粗い。要点だけ                                                 |
| まとまり | ファイルの中で閉じている         | 複数のファイルにまたがって集める                               |

- HTML は、原本をそのまま HTML にしたものではない。何を人間に見せるかを、docv が枠として決める。LLM を使わずに見せ方を決めるために、枠ごとに書き方の規格を持つ
- 原本は詳細として残し、必要なときに HTML のプロジェクト詳細のページから辿る
- 枠を docv/ に、原本を docs/ に置く。docv が形を決めるものと、プロジェクトが自由に書くものを、置き場所で分ける

```
枠（docv/）            ── 枠ごとのページ ──────▶ HTML（と、その JPG）
原本（Markdown、docs/）── 問いとタグのツリー ──▶ プロジェクト詳細.html
                       └─ mission ─────────────▶ AI Agent
```

## 部品

| 部品     | 何をするか                                                                    | 使う部品     |
| -------- | ----------------------------------------------------------------------------- | ------------ |
| ルール   | 原本と枠の書き方の決まり。人間と AI Agent の両方が従う                        |              |
| 検査     | 原本と枠がルールに沿っているかを確かめる（docv check）                        | ルール       |
| 書き換え | 整形と自動修正（docv fix）、枠のファイルの作成（docv add） | ルール、検査 |
| 出力     | 人間向けの HTML（docv build-html）と JPG（docv build-image）を作る | ルール       |

### ルール

- 原本: frontmatter に mission（答えること）、version（従う docv の版）、tags を書き、中身を mission への答えだけにする（[docs/rule/docs/guideline.md](../../docs/rule/docs/guideline.md)）
- 枠: docv/ に `<まとまり>/<ID>.<拡張子>` の名前で置く。16 の枠があり、当てはまらない枠は作らない（[docs/spec/slot.md](../../docs/spec/slot.md)）
- ADR: 決めた経緯と選ばなかった案は、docv/adr/ に決定 1 つを 1 つの Markdown で残す（[docs/spec/adr.md](../../docs/spec/adr.md)）
- docv.yaml: ツールの設定と、プロジェクト全体で共有する語彙（管理対象の範囲、タグの一覧）だけを書く（[docs/spec/config.md](../../docs/spec/config.md)）
- AI Agent には、`docv desc` がルールをまとめて渡す

### 検査

- frontmatter（mission と version があるか、タグが一覧にあるか）
- リンクの先があるか
- タグに付けたルール（過去の言い回し、終わったタスク）
- プロジェクトが選んだ書式の規則（太字、章番号など）と textlint
- 枠の名前、形、パスの先、include の先
- ADR の形と、打ち消す決定の指し先

### 書き換え

- fix は、textlint の自動修正をかけてから、決まった形に整形する。形は docv が決め、設定では変えない
- new は、ADR のパスなら ADR のテンプレ、枠のパスなら枠のテンプレ、それ以外なら Markdown のテンプレから作る

### 出力

- `docv build-html` は、人間向けの HTML（「HTML の構成」の章）を作る
- `docv build-image` は、枠のページの JPG（「JPG」の章）を作る

## HTML の構成

| ページ                | 中身                                                                                                                               |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| index.html            | プロジェクト概要。すべての枠のカードを、まとまりの見出しの下に横に並べる。置いていない枠のカードはグレーにする。カードの幅は固定で、収まらなければ横にスクロールする |
| ADR.html              | ADR の決定のつながりの図（group ごと）。ADR がないときは作らない                                                                   |
| プロジェクト詳細.html | 原本のツリー（タイトル、ファイル名、mission、タグ）                                                                                |
| 枠のページ            | `<まとまり>/<枠>.html`。枠の名前と、枠ごとの形の中身。ref だけの API 仕様書と DB 仕様書は、ページを作らずカードから直接リンクする |
| 原本のページ          | `プロジェクト詳細/<原本のパス>.html`（.md を .html にする）。原本 1 つを 1 ページにし、題を h1 にして本文をそのまま出す。右に、h2 と h3 の目次を置く |
| 決定のページ          | `ADR/<group>/<title>.html`。決定 1 つを 1 ページにする                                                                             |

- すべてのページの左に、プロジェクト概要、ADR、プロジェクト詳細へのサイドバーを置き、行き来できるようにする。枠のページはプロジェクト概要、決定のページは ADR、原本のページはプロジェクト詳細の項目に印を付ける
- 折りたたみは使わない。画像にしても、すべての中身が読めるようにするため。開閉するのは OS ごとの手順のタブだけ
- 見た目に凝らない。見出し、段落、箇条書き、表だけで出す

### 原本のツリー

- ディレクトリの中を、ファイル、ディレクトリの順に、それぞれ名前の順に並べる。すべての原本が 1 つのディレクトリ（docs/ など）の中にあるときは、そのディレクトリの行は出さない
- ディレクトリの行は薄い色の背景にして、ファイルの行と見分けられるようにする
- タグは frontmatter に書いた順に出す。タグごとに色を付ける。色は淡い 8 色で、ツリーの順に初めて出てきたタグから割り当て、足りなければ最初の色から使い直す
- 題から、原本のページへリンクする。ファイル名は出さない
- ファイルとタグの列は、中身の幅で折り返さずに出す。ミッションの列は残りの幅に 1 行で収め、はみ出た分は … にする（全文はマウスを載せると出る）。タグで絞り込んでも、列の幅は変えない
- 表の上に、タグのトグルを、タグごとの原本の数と一緒に並べる（例: `仕様 4`）。最初はすべてのタグを選んでいて、表を絞り込まない。すべて選んでいるときにタグを押すと、そのタグだけを選ぶ。それ以外のときは、押したタグの選ぶ・外すを切り替え、1 つも選ばなくなったら、すべて選んだ状態に戻す。一部のタグを選んでいるときは、選んだタグのどれかを持つ原本の行と、それを含むディレクトリの行だけを出す。選んでいないタグは薄く出す

### 原本のページの目次

- 原本のページの右に、h2 と h3 の見出しの目次を置き、見出しへのリンクにする
- 見出しには、GitHub と同じ形の id（同じ id が続けば -1、-2 を付ける）を付ける。原本の中の `#見出し` へのリンクも、そのまま使える
- 画面の幅が足りないときは、目次を出さない

## JPG

- `docv build-image` で、枠のページを 1 枚ずつ JPG にする
- JPG にするのは、yaml から作る枠のページだけ。Markdown から作るページ（md の枠、決定のページ、原本のページ）は、GitHub でそのままプレビューできるので JPG にしない
- 置き場所は `jpg/<まとまり>/<枠>.jpg`（例: `jpg/サービス仕様/利用マニュアル.jpg`）。画像を探しやすいように、HTML の見出しと同じ和名にする
- GitHub は、リポジトリの中の HTML を描画しない。JPG なら、ホスティングしなくても GitHub で見られる。README などに `![利用マニュアル](docv/build/jpg/サービス仕様/利用マニュアル.jpg)` のように埋め込める
- 印刷の表示にして撮る。サイドバーは写さず、OS ごとの手順のタブは、すべての OS を並べて写る

## 後から入れる

- docv が管理するのは、docv.yaml の docs に当てはまるファイルだけ。それ以外のファイルは、管理外として自由に置ける
- 既存のプロジェクトには、全部を管理外にした状態から、少しずつ管理対象と枠を足していける。`docv migrate-guide` が、次にやることを示す

## docv がしないこと

| しないこと                                      | 代わりに                                                                                                                                                   |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 図、API の定義、DB のスキーマの形式を決めること | それぞれに向いた外の道具（LLM で描いた SVG、OpenAPI など）で作り、枠からリンクするか埋め込む。docv は全体の枠組みと見せ方を持ち、外の道具は中身の作り方を持つ |
| プラグインの規格                                | 責務の分け方として上のように考え、仕組みは作らない                                                                                                         |
| AI Agent 向けの Skill や plugin の提供          | ルールファイルを `docv desc` で出す。ルールに従って直させる作業は、利用者が AI Agent に頼む                                                                |
| CLAUDE.md や hook の設定                        | 入れたい利用者が自分で書く                                                                                                                                 |
| CI での実行                                     | すべてローカルで実行する                                                                                                                                   |
| 実装とのずれの検出                              | 枠に書いたパス（ディレクトリの枠の path など）がなくなったことだけを check で知らせる                                                                                    |
| 変更履歴を書くこと                              | 変更は git と PR に残す。決めた経緯と選ばなかった案は ADR に残せる                                                                                         |
