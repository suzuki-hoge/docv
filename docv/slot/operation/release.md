# リリース

版は `Cargo.toml` の `version` で決め、版のタグを push する。バイナリは配らず、利用者は GitHub のソースから cargo で入れる（[インストール](../service/install.yaml)）。

## 手順

1. `assets/update-guide.yaml` の先頭に、その版の変更点と対応を足す。コミットはしない
   - 対応のない版も書く
   - docv update-guide が出す 1 行は 100 文字以内にし、収まらない変更は分ける。長すぎると、次の手順の途中の cargo test が落ちる
2. 人間が `make new-version` を実行する

   ```sh
   make new-version V=2.2.0
   ```

版を手で書き換えない。版上げのコミットとタグを、毎回同じ形にするため。

`make new-version` は、次を順に行う。

1. 始める前に、次を確かめる
   - main にいて、origin の main を取り込んである
   - 手元の変更が `assets/update-guide.yaml` だけで、その先頭が渡した版になっている
   - 渡した版が今の版より新しく、その版のタグがまだない
2. 版を書く場所（`Cargo.toml`、`Cargo.lock`、`docv.yaml` の `docv_version`、設定ファイルのページの例）を、新しい版に書き換える
3. 古い版が、決まった場所（版ごとの変更点、ADR、PDR、作り直す出力など）の外に残っていないかを探す
4. `make fix` で確かめ、HTML とインデックスを新しい版で作り直す
5. 「版を x.y.z にする」でコミットし、v で始まるタグを打ち、main とタグを push する

### 止まったとき

| 止まったところ               | 直し方                                                                                                      |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 始める前の確かめ             | 表示に従って直す。何も書き換えていない                                                                      |
| 版の書き換えか、古い版の探し | 版を書く場所が増えたか、書き方が変わった。`scripts/new-version.sh` の書き換える場所か、残してよい場所を直す |
| `make fix`                   | 指摘を直す。書き換えは元に戻してあり、`assets/update-guide.yaml` はそのまま残る                             |
| push                         | コミットとタグは手元に残っている。表示されたコマンドで push し直す                                          |

途中で止まったら、直してからもう一度 `make new-version` を実行する。

タグは、`docv init` と `docv slot gen` がファイルの 1 行目に書くスキーマの URL の参照先になる。タグを push するまで、その版の URL は開けない。
