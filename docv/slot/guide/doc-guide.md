# Doc ガイド

このプロジェクトでドキュメントを書く人間と AI Agent は、このページに従う。

`docv gen doc-guide` が作った雛形を、プロジェクトに合わせて直して使う。docv が決めるルール（ディレクトリ、ミッション、ADR と PDR の章など）は `docv desc` にあり、このページには書き方のガイドラインだけを書く。

docv の目的は、人間がプロジェクトの今の姿をいつでもざっと把握できるようにすることである。

ドキュメントは、プロジェクトについて知りたいときや、サービス仕様とシステム仕様を変えるときに、判断の材料として読まれる。

ドキュメントには、次の 3 つを書く。

- Slot: およそどのプロジェクトでも要ること（サービス仕様、環境構築など）
- Free ファイル: プロジェクトに特有の詳しいこと
- ADR と PDR: 意思決定の背景と、決めたこと

## 1. Slot

### 言葉の使い分け

あいまいな言葉は、次のように使い分け、書く場所を決める。

| 言葉           | 指すもの                                                                                                                                               | 書く場所                                                                                            |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| サービス説明   | docv をなにも知らない利用者へ伝える最初の説明                                                                                                          | サービス概要                                                                                        |
| サービス仕様   | 外から見た機能、振る舞い、決まり。実装をそっくり差し替えても変わらないこと<br>利用者、AI Agent、開発者が読む                                           | 要点はサービス仕様の 1 ページ目（`docv desc`）<br>詳しいことは 2 ページ目以降                       |
| システム構成   | 部品（CLI、リポジトリのドキュメント、textlint、git、出力など）の構成と役割、部品の間の流れ、どの処理をどの部品で行うか<br>開発者が判断を下すときに読む | 全体像はシステム概要。SVG で描く<br>部品ごとの詳しいことはシステム仕様                              |
| アーキテクチャ | システム全体で採る方式と決まり（部品の分け方、通信の方式、非同期処理の実現方法など）<br>部品を足したり、つなぎ方を変えたりするときに読む               | アーキテクチャ<br>その方式を選んだ理由は ADR                                                        |
| サービスエラー | 利用者が書いたドキュメントや渡した引数が原因で起きるエラー<br>例: check の指摘、`docv.yaml` の誤り、終了コード                                         | サービス仕様の 2 ページ目以降                                                                       |
| システムエラー | 環境や外の道具が原因で起きるエラーと、その扱い<br>例: textlint に要る Node.js が見つからない、ルートが git の管理下にない                              | システム仕様                                                                                        |
| 実装の決まり   | コードを書くときに従う決まり。コードを読んでも、守るべき決まりか、たまたまそうなっているかが分からないこと                                             | コード全体にかかるものは設計・実装<br>1 か所に置けるものは、そのコードのコメント                    |
| 実装           | 1 つの部品の中の今の作り（関数やモジュールの分け方、処理の手順）                                                                                       | 書かない。コードを読めば分かる                                                                      |
| 設計           | 何かを判断し決めること。ドキュメントの種類ではない                                                                                                     | 決めたいことは `docv/free/plan/`<br>決めた結果はミッションに沿うファイル<br>経緯や廃案は ADR か PDR |

サービス仕様とシステム仕様は、利用者に見える結果か、それを実現する方法かで書き分ける。

次に例を示す。

| 書きたいこと | サービス仕様に書くこと                          | システム仕様に書くこと                               |
| ------------ | ----------------------------------------------- | ---------------------------------------------------- |
| 出力         | HTML のページの作りと、毎回同じ出力にする決まり | 出力先を作り直し、埋め込んだ CSS と JS を書く流れ    |
| エラー       | check の指摘と終了コード                        | 外の道具が見つからないときや、やりとりが途切れたとき |
| スキーマ     | `docv.yaml` の項目                              | スキーマを埋め込み、版のタグの URL で公開すること    |
| 外の道具     | textlint で確かめる項目と、使うかどうかの設定   | どのコマンドが、どの道具を、いつ呼ぶか               |

### ページの分け方

ページに分けられる Slot は、次のどれかに当たったら分ける。分けておく理由のないページは、まとめる。

- 読み手の違う情報が混ざっている
- 読むタイミングの違う情報が混ざっている
- 違う部品や機能の情報が混ざっている

サービス仕様の 1 ページ目は、`docv desc` と同じ `desc.md`（`assets/desc.md` へのシンボリックリンク）にする。`docv desc` と一致させるため、このページは 1 ファイルのまま保ち、AI Agent が最初に読む要点だけを書く。詳しいことは 2 ページ目以降に書く。

## 2. Free

- 足す前に、`docv list` で、Slot のミッションに当たらないかを確かめる
  - 当たるなら、その Slot に書く
- 1 つのファイルの `mission` は、1 つの用途にする
- ディレクトリを細かく設計せず、タグで分ける
  - 複数の属性を持つファイルは、ディレクトリでは置き場所が定まらないため
  - Slot の代わりになるディレクトリ（spec/、architecture/ など）ができそうになったら、Slot のページの分け方を見直す

このリポジトリでは、次のタグを使う。

| タグ     | 書くこと                                                 |
| -------- | -------------------------------------------------------- |
| スキーマ | `docv.yaml` の JSON Schema の写し（`docv/free/schema/`） |

## 3. ADR

今の姿は Slot と Free ファイルに書き、なぜそうなったかを ADR と PDR に残す。

なぜやらなかったかは今の姿に残らないので、意思決定の履歴を残すことに価値がある。

### 書くとき

ADR（Architecture Decision Record）は、次のすべてに当たる技術の決定のときに書く。

- 複数の案を比べて選び、選んだ理由が今のドキュメントやコードからは読み取れない
- 長く効き、後から変えるのに手間がかかる（使う言語、IaC の道具、部品の分け方、API の形、データの持ち方など）
- 実装の方法を変えても覆らない（コードを少し直せば正せるものは当たらない）

### 書かないもの

ADR と PDR のどちらにも、次のものは書かない。

- 今の決定を変えずに直したこと（バグ修正、考慮漏れの手当て）
  - 理由を残したいときは、コミットメッセージに書く
- 決定に従って選ぶ細部（関数名、環境変数名、ライブラリの細かな使い方、画面の文言など）
- 移行の計画や進み具合など、短い間に状態が変わること

### 書き方

ADR と PDR の両方で、次のように書く。

- 1 つの記録には、決定か変更を 1 つだけ書く
- 技術とプロダクトの両方にまたがるときは、仕様の変更を PDR に、それを実現する技術の決定を ADR に分け、「参考」の章で互いにつなぐ
- その記録だけで読めるように書く
  - 根拠は、後から確かめられるファイルや資料へのリンクにし、「参考」の章にまとめる
  - 会議や口頭でしか確かめていないことを根拠にしない
  - 決めた理由を、Issue や PR の番号に預けない
- 決めたことは、実装の自由を奪わない粒度で書く
  - 決めたことを守ったまま細部を差し替えたとき、本文を書き換える必要があるなら、その細部は書かない

## 4. PDR

PDR（Product Decision Record）は、サービス仕様についての ADR に当たる。

- 料金、プラン、提供する機能の範囲、対象とする利用者、サポートの方針などの変更
- やらないと決めたこと、やめたこと
  - 同じ案がまた出たときに、理由を示せるようにするため

書かないものと書き方は、ADR と同じ。見直す条件は、当たったかどうかを後から客観的に判断できる形で書く。

## 5. ドキュメントの外に書くこと

次のことは、ドキュメントの外に置く。

| 書くこと                           | 置き場所                                                                                                            |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 値や設定を変える人に要る理由       | その値の隣のコメント                                                                                                |
| 部品の作り                         | 部品のコメント                                                                                                      |
| テーブルや列の意味                 | スキーマのコメント（生成したテーブル仕様書に出る）                                                                  |
| 確かめるケース                     | テスト名                                                                                                            |
| 検証器やリンタで守らせている決まり | 検証器やリンタの文（コメント、エラーの文）                                                                          |
| 使う人に毎回伝えるべき注意         | 製品やスクリプトの確認や文<br>言わせられないときだけドキュメント                                                    |
| AI Agent の作業の進め方            | エージェントの指示ファイル                                                                                          |
| 予定、未決、実装の状態、調査や議論 | `docv/free/plan/`<br>解決して消すことが前提<br>いかなるファイルからもここの具体ファイルにリンク・言及してはならない |
| 作業の報告、確かめてほしいこと     | コミットメッセージ                                                                                                  |
| 作業メモ                           | ルートの `tmp/`（コミットしない）                                                                                   |

## 6. 書かないもの

読者が自分で知れることは書かない。

- 一般的な知識（Nginx とは何かなど、調べれば分かるもの）
- コード、設定、生成物、テストを読めば分かること
  - プロジェクトを調べれば分かる細部は、原則としてドキュメントで説明しない
  - コードの決まりやテストのパターンの説明は、ドキュメントではなく、コードのコメントに書く
- 安全に実行でき、結果を見れば分かること
  - 例: 安全装置のある道具について、実行する前の条件を細かく並べない
  - 例: リンタを実行すれば分かることを、ドキュメントの決まりとして細かく書かない
- 時系列の記録や、作業の報告
- 今はない、過去の情報（廃止したことは、決定として ADR か PDR に書く）

## 7. 共通の書き方

### ページ

- 今の姿だけを書く
  - 経緯は ADR か PDR に、やったことはコミットメッセージに書く
  - 変わった情報は上書きし、古くなった情報は消す
  - 仕様は、実装の状態（未実装、止めている）にかかわらず、あるべき姿として書く
- 結論から書き、前置きや、同じことの言い換えを書かない
- 型（表の列、決まった見出し）を先に決める
- 「補足」「注意点」「残るリスク」のような受け皿の節を作らない
  - 残るものは、原因になった決定の隣に「そのため、次のことは残る」と書く
- 読者に置き換えをさせない
  - 環境ごとに変わる値は、表の列にする
  - コマンドは、「変える値の行」と「そのまま貼れるブロック」にする
- 用語集の言葉で書く
- 行番号や章番号のような、すぐ変わるものを頼りに書かない
- ほかのページへの案内は、書かないのを基本にする
  - Slot はミッションで、ほかのページは HTML の検索で辿れる

### 箇条書きと折りたたみ

- 箇条書きは 1 項目 1 文にする
  - 2 文以上になるなら、子の項目に分ける
  - 別々の決まりは、別の項目にする
- 畳むのは、必要になってから読む詳しいこと（全項目の一覧、例、例外の扱い、理由の細部など）
  - 読む人の誰もが知っておく要点と決まりは畳まない
  - 畳んだところを読まなくても、話が通るようにする
  - `<summary>` を見るだけで、中に何があるかが分かるようにする
  - 消すべきものは、畳んで残さずに消す

### 図

- 分岐や合流、多対多のつながり、状態の移り変わりは、SVG の図にし、その分の文を消す
  - 上から順に実行する一本道の手順は、箇条書きのままにする
  - アスキーアートは使わない
- 図と同じことを、本文で説明しない
- 図は、今の構成に合わせて直す

## 8. AI Agent への指示

- セッションの初めに `docv desc` と `docv list` を実行し、このページに従う
- ドキュメントを変えたら、`docv fix` を通す
- 書く前に
  - 理由や決まりは、コードとコメントを探し、同じことがあれば写さない
  - 実装は、指示がない限り書かない
  - 長い手順や注意は、製品やスクリプトに言わせられないかを人間に提案する
  - 決まりを変えるときは、関わる ADR と PDR を探す
- 書いた後に
  - 手順を書いたら読者としてなぞり、戻せないこと、戻している間の振る舞い、気づけないことが書いてあるかを確かめる
  - 既存の文書を Slot に移したら、ミッションに当たらない記述を、ほかの Slot、Free ファイル、ADR、PDR に分ける
  - 実装は、Slot に移さない
- 直すよう言われたら、消す・移すを先にし、割る・畳むは後にする
- ADR と PDR
  - 加筆の指示があるまで作らない
  - 「ADR」と「PDR」の章で書くとしたものに当たる状況では、作ることを提案する
  - 書いたら、このページの基準で見直してから人間に見せる
  - PDR の見直す条件を満たす状況に気づいたら、その PDR を示して見直しを提案する
- このページに合わない記述を、作業中に 2 つ以上のファイルで見つけたら、作業を終えてから `docv review-guide` でのレビューを提案する
  - リリースの前や、大きな機能を入れた後にも提案する
