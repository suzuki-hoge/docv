# Doc ガイド

このプロジェクトのドキュメントを書く・直すときの方針。人間と AI Agent の両方が従う。

本ファイルは `docv slot gen doc-guide` が作った雛形で、プロジェクトに合わせて調整し利用する。

`docv desc` で定義されるルール、設定、ガイドラインのうち、このページはガイドラインについての指示ファイルである。

## どこに何を書くか

| 書く内容                                                          | 書く場所                                                                                                            |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| およそ普遍的に必要と思われること<br>Slot のミッションに当たること | Slot ファイル                                                                                                       |
| それ以外のプロジェクト固有の詳細情報                              | Free ファイル<br>`mission` 属性で AI Agent が一貫した用途で加筆できる目印にする                                     |
| 技術の意思決定や経緯、背景、取らなかった選択など                  | ADR（Architecture Decision Record）                                                                                 |
| プロダクトやサービスの仕様の変更と、その理由や経緯                | PDR（Product Decision Record）                                                                                      |
| タスクごとの詳細調査や議論                                        | GitHub Issue                                                                                                        |
| 作業予定                                                          | `docv/free/plan/`<br>解決して消すことが前提<br>いかなるファイルからもここの具体ファイルにリンク・言及してはならない |
| まとまっていない意思決定やメモ                                    | `docv/free/tmp/`<br>解決して消すことが前提<br>いかなるファイルからもここの具体ファイルにリンク・言及してはならない  |

## 言葉の使い分け

docv の文脈においては、あいまいな「仕様」という言葉を避け次のように定義している。どのファイルになにを書くべきかの拠り所にすること。

| 言葉           | 指すもの                                                                                                                                                                 | 書く場所                                                                                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| サービス説明   | docv をなにも知らない利用者へ伝える最初の説明                                                                                                                            | サービス概要                                                                                                                                                   |
| サービス仕様   | 外から見た機能、振る舞い、決まり。実装をそっくり差し替えても変わらないこと<br>利用者、AI Agent、開発者が読む                                                             | 要点はサービス仕様の 1 ページ目（`docv desc`）<br>詳しいことは 2 ページ目以降                                                                                  |
| システム構成   | 部品（CLI、リポジトリのドキュメント、textlint、Chrome、出力など）の構成と役割、部品の間の流れ、どの処理をどの部品で行うか<br>開発者が判断を下すときに読む                | 全体像はシステム概要。SVG で描く<br>部品ごとの詳しいことはシステム仕様                                                                                         |
| アーキテクチャ | システム全体で採る方式と決まり（部品の分け方、通信の方式、非同期処理の実現方法など）<br>部品を足したり、つなぎ方を変えたりするときに読む                                 | アーキテクチャ<br>その方式を選んだ理由は ADR                                                                                                                   |
| サービスエラー | 利用者が書いたドキュメントや渡した引数が原因で起きるエラー<br>例: check の指摘、`docv.yaml` の誤り、終了コード                                                           | サービス仕様の 2 ページ目以降                                                                                                                                  |
| システムエラー | 環境や外の道具が原因で起きるエラーと、その扱い<br>例: Chrome が見つからない、Chrome とのやりとりが途切れる                                                               | システム仕様                                                                                                                                                   |
| 実装の決まり   | コードを書くときに従う決まり。コードを読んでも、守るべき決まりか、たまたまそうなっているかが分からないこと（フレームワークの使い方、ディレクトリやコーディングの決まり） | 設計・実装                                                                                                                                                     |
| 実装           | 1 つの部品の中の今の作りで、コードを読めば分かること（関数やモジュールの分け方、処理の手順）                                                                             | 書かない<br>原則として必要とするのは AI Agent であり、それにとってはコードから自明であるため                                                                   |
| 設計           | 何かを判断し決めること。ドキュメントの種類ではない                                                                                                                       | 決めたいことは `docv/free/tmp/` や GitHub Issue<br>決めた結果はミッションに沿うファイル（コードを書くときに従う決まりは設計・実装）<br>経緯や廃案は ADR か PDR |

サービス仕様、システム仕様、開発コマンド、アーキテクチャ、設計・実装、テスト方針、インフラと環境は、複数ページに分割できる。明確な分割点は docv では指定しないが、およそ次のような観点でページが肥大化しすぎないよう分割するといい。

- 読み手の違う情報がページに混在している
- 読むタイミングの違う情報がページに混在している
- 異なるコンポーネントや異なる機能の情報がページに混在している

サービス仕様の 1 ページ目は、`docv desc` と同じ `desc.md`（`assets/desc.md` へのシンボリックリンク）にする。`docv desc` と一致させるため、このページは 1 ファイルのまま保ち、AI Agent が最初に読む要点だけを書く。詳しいことは 2 ページ目以降に書く。

### 書き分けの例

| 種類     | サービス仕様                                    | システム仕様                                         |
| -------- | ----------------------------------------------- | ---------------------------------------------------- |
| 出力     | HTML のページの作りと、毎回同じ出力にする決まり | Chrome を動かして JPG を撮る流れ                     |
| エラー   | check の指摘と終了コード                        | 外の道具が見つからないときや、やりとりが途切れたとき |
| スキーマ | YAML の Slot と `docv.yaml` の項目              | スキーマを埋め込み、版のタグの URL で公開すること    |
| 外の道具 | textlint で確かめる項目と、使うかどうかの設定   | どのコマンドが、どの道具を、いつ呼ぶか               |

## 望ましいドキュメント

- 概要と詳細が適切に分類されている
  - 概要は要点がまとまっていて、詳細は `<details>` で折りたたみ必要なときのみ視認できるようになっている
- 現在の情報が整理されている
- 用語集の単語に沿って書かれている
- 事実と予定・課題管理を混ぜない

## 望ましくないドキュメント

- `mission` の示す内容が一意になっていない / ひとつのファイルに複数の内容を混ぜている
- 過去の情報がすべて羅列されている → 今現在知らなくていいことは随時削除し、必要な経緯は ADR か PDR に移す
- 同じ内容が複数の箇所に書いてある
- 実装が書いてあり、コードを変えるたびに直す必要がある
- Slot のミッションに当たる内容が、Free ファイルに置かれている
- コードの行番号やドキュメントの章番号など、頻繁に変更される情報に依存している

## ADR と PDR の作成基準

ADR と PDR は、長く読み返される記録である。今の姿は Slot と Free ファイルに書き、ADR と PDR には、なぜそうなったかを残す。置き場所と章立ては `docv desc` の「ADR」と「PDR」に従う。

| 記録 | 残すもの                                                 | 目的                                                                                                                                     |
| ---- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| ADR  | 技術の決定                                               | なぜその技術や構成を選んだのかを残し、後から変えるときの判断に使う                                                                       |
| PDR  | プロダクトやサービスの仕様の変更（足す、変える、やめる） | なぜ今の仕様になったのかを、将来も分かるようにする。仕様を変えるときや、見送った案がまた出たときに、当時の理由と前提を確かめられるように |

### ADR に書くもの

次のどちらにも当たる技術の決定を書く。

- 複数の案を比べて選んだ決定で、選んだ理由が今のドキュメントやコードからは読み取れない
- 長く効き、後から変えるのに手間がかかる。たとえば、使う言語、IaC の道具、部品の分け方、API の形、データの持ち方

### PDR に書くもの

PDR は、仕様がどう変わってきたかの履歴である。案を比べて選んだ決定に限らない。仕様を足す・変える・やめるとき、その理由が今のドキュメントからは読み取れないなら書く。

- 料金、プラン、提供する機能の範囲、対象とする利用者、サポートの方針などの変更
- やらないと決めたこと、やめたこと。後から同じ案が出たときに、なぜやらないのかを示せるように

### 書かないもの

| 記録 | 書かないこと                                                                         | 代わりに書く場所                                   |
| ---- | ------------------------------------------------------------------------------------ | -------------------------------------------------- |
| ADR  | バグ修正や考慮漏れの手当てなど、今の決定を変えずに直したこと                         | 書かない<br>理由を残したいときはコミットメッセージ |
| ADR  | 比べた案がなく、理由を残すまでもない決定                                             | 書かない                                           |
| 両方 | 決定に従って選ぶ細部（関数名、環境変数名、ライブラリの細かな使い方、画面の文言など） | 書かない<br>コードから読める                       |
| 両方 | 移行の計画、進み具合、タスクの一覧、期間を区切った施策など、短い間に状態が変わること | `docv/free/plan/` や GitHub Issue                  |

### 書き方

- 1 つの記録には、決定か変更を 1 つだけ書く
- 技術とプロダクトの両方にまたがるときは、仕様の変更を PDR に、それを実現する技術の決定を ADR に分けて書き、「参考」の章で互いにつなぐ
- その記録だけで読めるように書く。会議や口頭でしか確かめていないことを根拠にしない。根拠は、後から確かめられるファイルや資料へのリンクにし、「参考」の章にまとめる
- 決めたことは、実装の自由を奪わない粒度で書く。細かさは「決めたことを守ったまま細部を差し替えたとき、本文を書き換える必要があるか」で確かめる。必要なら、その細部は書かない
- PDR の見直す条件は、当たったかどうかを後から判断できるように書く。「利用者が増えたら」のような、いつ当たったか分からない書き方をしない
- 決めた理由を、Issue や PR の番号に預けない。番号だけでは、記録を読んでも理由が分からない

## タグ

Free ファイルにはタグをつけ、ディレクトリを細かく設計せずにタグで分類する。いちばんの目的は、ディレクトリの構造によるドキュメントの管理が破綻しやすいことを避けるため。往々にして複数の属性を持つファイルがあり、ディレクトリで分けると置き場所が定まらない。タグで分類すると、HTML で絞り込んで閲覧しやすくもなる。

| タグ     | 書くこと                                                                 |
| -------- | ------------------------------------------------------------------------ |
| スキーマ | `docv.yaml` と YAML の Slot の JSON Schema の写し（`docv/free/schema/`） |

## AI Agent への指示

- セッション開始時に `docv desc` を実行し、本ファイルの指示に従いドキュメント管理をすること
- Slot ファイルのスキーマは `docv slot` 系コマンドで確認すること
- ドキュメント変更時は `docv fix` を通すこと
- ドキュメントを書き足すときは、増えた情報を適切な量で反映すること
- 実装は、指示がない限り書かないこと
- Free ファイルを足す前に、その mission がどれかの Slot のミッションに当たらないかを確かめること。当たるなら、その Slot に書き、長くなるならページに分けること
- Free ファイルに spec/ や architecture/ のような、Slot の代わりになるディレクトリができそうになったら、Slot のページ（タブ）の分け方を見直すこと
- 既存の文書を Slot に移すときは、ミッションに当たらない記述を、ほかの Slot、Free ファイル、ADR、PDR に分けること。実装は移さないこと
- 変わった情報は原則として上書きし、古くなった情報は原則として抹消すること
- ADR と PDR は加筆の指示があるまで作成せず、「ADR と PDR の作成基準」の書くものに当たる状況では作成提案にとどめること
- PDR の見直す条件を満たす状況に気づいたら、その PDR を示して、見直しを提案すること
- 検討中の項目、メモ、課題などを管理する場合は、正式ドキュメントとは分けて管理すること
  - タグや `docv.yaml` の `docv_exclude` を活用すること
- アスキーアートを用いたいときは、まず SVG で作図すること
- 画像は `docv desc` の「画像」の置き方に従い、使うファイルの隣に置くこと
