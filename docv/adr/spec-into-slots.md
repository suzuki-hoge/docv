# docv 自身の設計は Slot に書き、spec には規格の詳細だけを残す

## 背景

docv 自身の設計を `docs/spec/` の 15 ファイルに書いていた。Slot を作ってからは、サービス仕様、システム仕様、利用マニュアル、インストール、デプロイとリリースの Slot に書いたことが spec にもあり、2 か所で揃え続けることになっていた。

## 決めたこと

Slot の問いに答える内容は Slot に書き、spec と重なる記述は消す。`docs/` には、どの Slot の問いにも収まらない docv の規格の詳細（原本の書き方、Slot、ADR、`docv.yaml`）だけを残す。コマンドの挙動は利用マニュアルの `details` に、内部の決まりはシステム仕様に書く。

## 結果

spec は `slot.md`、`adr.md`、`config.md` の 3 つになり、原本の書き方は `rule/docs/guideline.md` に置く。`docv desc` のルールファイルの元は、この 4 つになる。docv 自身が、Slot に書けばドキュメントが足りることを示すサンプルになる。

## 選ばなかった案

| 案                                         | 選ばなかった理由                                                                     |
| ------------------------------------------ | ------------------------------------------------------------------------------------ |
| spec を正本にし、Slot からはリンクする     | Slot の問いの答えが Slot の中でそろわない。Slot は詳しいことも Slot の中に書く決まり |
| spec を Slot の `include` で埋め込む       | コマンドごと、章ごとに埋め込むことになり、どこに何があるかが分かりにくい             |
| `docv.yaml` の詳細も利用マニュアルに入れる | 利用マニュアルのページが長くなりすぎる。`docv.yaml` は規格として spec に残す         |
