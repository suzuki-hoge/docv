# Doc ガイド

このリポジトリのドキュメントを書く・直すときの方針。人間と AI Agent の両方が従う。

このファイルは、`docv slot gen doc-guide` の雛形をもとに、このリポジトリに合わせて直したもの。`docv slot gen doc-guide` が出す内容とは一致しない。雛形は `docv slot gen doc-guide --print` で確認する。

docv の決まりは、[ルール](../service/words.yaml#決まりの種類)、[設定](../service/words.yaml#決まりの種類)、[ガイドライン](../service/words.yaml#決まりの種類) に分かれる。このページは、ガイドラインを書く。

---

## 1. どこに書くか

まず、書くべき変更かを決める。docv の振る舞い、ルール、設定が変わったときだけ書く。コードを変えただけなら、書かないのが正しい。

| 書く内容                                     | 書く場所                                                                               |
| -------------------------------------------- | -------------------------------------------------------------------------------------- |
| docv の設計（Slot のミッションに当たること） | Slot（`docv/`）。docv に当てはまる Slot だけを置く                                     |
| どの Slot にも収まらないルールの詳しいこと   | `docs/spec/`（Slot、Free ファイル、ADR、`docv.yaml`）                                  |
| 決めた経緯、選ばなかった案                   | ADR（`docv/adr/`）                                                                     |
| まだ決まっていないこと                       | [`docs/fixme/open.md`](../../docs/fixme/open.md)。決まったら Slot か spec に書いて消す |
| やると決めたタスク                           | `docs/plan/`。終わったら消す                                                           |
| やったこと                                   | コミットメッセージ                                                                     |
| まとまっていない意思決定やメモ               | `docs/tmp/`。ほかのドキュメントからリンクも言及もしない                                |

- 決めたことが変わったら、Slot か spec を書き換え、決めた経緯を ADR に残す。ADR の形は [`docs/spec/adr.md`](../../docs/spec/adr.md)
- 同じことを 2 か所に書かない。ほかのファイルにあることは、リンクにする
- `docs/plan/` と `docs/tmp/` は `docv.yaml` の `ignore` に入れてあり、HTML に出さない
- `docs/` にファイルを足したり消したりしたら、`README.md` のドキュメントの一覧を直す

## 2. Slot と spec の書き分け

- サービス仕様: `docv desc` が出す概要と同じファイル（`assets/desc.md` へのシンボリックリンク）。直すと `docv desc` の出力も変わる
- 利用マニュアル: コマンドごとに、何をするか、オプション、例を書く
- システム仕様: 外から見えない決まり（埋め込むもの、HTML の作り、毎回同じ出力にする決まりなど）を書く
- 用語集: docv の言葉の定義を書く。ほかのファイルには書き写さない
- spec: Slot のミッションに収まらないルールの詳しいこと（項目の一覧、check の ID など）だけを書く。`docs/schema/` には、スキーマの写しを置く

## 3. mission

- このファイルを読むと何が分かるかを、1 文で書く。「〇〇を知りたければこのファイル」と分かるようにする
- ファイルの中身は、`mission` に収まることだけにする

---

## 4. タグ

| タグ   | 書くこと                                    | ルール          |
| ------ | ------------------------------------------- | --------------- |
| 仕様   | docv の振る舞い、今の状態の理由             | no-past-wording |
| ルール | docv の仕組みが決める決まり（スキーマなど） |                 |
| 設定   | `docv.yaml` で切り替えること                |                 |
| 出力   | HTML と JPG の出し方                        |                 |
| 未決   | まだ決まっていないこと                      |                 |

---

## 5. 書き方

- 今の姿だけを書く。前の内容を直接書き換え、古い内容は消す
- 本文には要点を書き、細かい理由、例外、例は `<details>` に入れる
- まとめ直しの節（一覧表、流れのまとめなど）を作らない。本文と重なり、どちらを直すかが分からなくなる
- 括弧の補足は、1 文に 1 つまでにする。表のセルに長い文を入れない。箇条書きの入れ子は浅くする
- `mission` に収まらない内容は、別のファイルに書く。内容を収めるために、`mission` を広げない

---

## 6. コードとドキュメント

- コードのコメントは、実装が従う Slot か spec を、パスと章で指す（例: `docs/spec/free.md の 3 章`）。ドキュメントを動かしたら、コメントも直す
- AI Agent は、ADR を決めた理由を聞かれたときだけ読み、`docv build` の出力は読まない

---

## 7. 書式

機械で確かめられるものは、[`docv.yaml`](../../docv.yaml) の `lint` と textlint で確かめる。ドキュメントを変えるたびに `docv fix` と `docv check` を通す。

- 日本語で書く。Markdown の太字（`**`）は使わない。強調したいときは、見出し・箇条書き・表で構造を分ける
- 金額は `$` を使わず、「3 ドル」のように書く。GitHub は `$` で挟まれた部分を数式として表示するため
- 冒頭の 1〜2 行で、そのファイルが決めることと、関連するファイルへのリンクを書く
- 章には番号を振り（`## 1. 〇〇`）、章の間は `---` で区切る
- `docs/` の中のファイルへのリンクは、表示する文字を `docs/` からのパスにする（例: `spec/slot.md`）。`docs/` の外からのリンクは、ルートからのパスにする
- ルートの `tmp/` は作業用。コミットせず、ほかのドキュメントからリンクしない
