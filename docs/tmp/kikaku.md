# docv の規格にない情報

性質の違う 4 つのプロジェクト（サーバー、クライアントアプリ、サーバーとクライアントを含む Web サービス、サーバーを持たない業務の自動化）のドキュメントを、今の 15 の枠に当てはめて、収まらないものを集めた。数は、4 つのうちいくつで見つかったか。

---

## 1. 枠に入らない情報

| 種類                         | 数  | 中身                                                                                         | 枠に入らない理由                                                       |
| ---------------------------- | --- | -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| AI Agent 向けの指示と権限    | 4   | やってよいこと、禁止の git 操作、確認が要るコマンド、hook、スキル、AI 用の読み取り専用の DB ユーザー | 読み手が AI。システムの事実ではなく、作業者の振る舞いと権限の決まり     |
| 未実装、未決、予定           | 4   | 仕様にあるが実装していないもの、確かめていないこと、今後の予定、コードの TODO                 | 今の姿ではなく、今との差分や将来                                       |
| コーディング規約             | 4   | 層の分け方と import の向き、lint の設定、レビューの観点、デザインの方針（色、余白）           | システムの事実ではなく、書く人への決まり                               |
| 意思決定の記録               | 3   | 比べた候補、採用しなかった案と理由、1 回きりの変更の説明。更新せず新しい記録で否定する運用   | 時系列の記録。枠は今の姿だけを書く                                     |
| 運用手順と障害対応           | 3   | 本番 DB への手作業のマイグレーションと戻し方、通知ごとの対処、止め方と再開、月次の見直し、調査用の SQL | 何か起きたとき、決まった時期にやること。利用マニュアルは日常の操作     |
| 開発の進め方                 | 3   | 1 課題 = 1 ブランチ = 1 PR、仕様を書き換えてから生成し、確かめてから実装する順番             | 開発者コマンドは「何を打つか」で、順番と「誰が何をしてよいか」は表せない |
| テスト方針と CI の方針       | 3   | 何をテストし何をしないか、警告も失敗にする、自動修正の差分があれば失敗                       | 判断の決まりで、コマンドの一覧ではない                                 |
| ドキュメントの運用ルール     | 3   | ディレクトリごとの読み書きの権限（人間か AI か）、生成物は手で直さない、作成者の記録        | 文書そのものの管理規約                                                 |
| 外とのつながり               | 3   | 別のリポジトリから取り込む仕様の版の合わせ方、外のサービスの規約から来る禁止事項             | 中身ではなく、外との依存と、外の決まりが理由になっていること           |
| 権限とアカウント             | 2   | サービスアカウント、ロール、誰の権限で動くか、人が加わる・抜けるときの鍵の手順、値を人に聞く | 環境変数は key と置き場所だけで、誰がどの権限を持つかは表せない         |
| 画面一覧と画面遷移           | 2   | 画面、目的、主な要素、タブと遷移                                                             | 利用マニュアルは操作の手順で、画面の一覧ではない                       |
| 戦略と目標値                 | 1   | 誰に届けるか、目標の数字、見直しのサイクル                                                   | サービス仕様は「何であるか」で、狙いと数字は入らない                   |
| 人が決めること               | 1   | 支出の上限、通知先など、人の判断が要る項目の一覧                                             | 決定待ちの一覧                                                         |
| 作業計画                     | 1   | 一時的なタスク                                                                               | 今の姿ではない                                                         |

## 2. 枠には入るが、今の形では表しにくいもの

| 枠                   | 表しにくいこと                                                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 07、08、12 にまたがる | どれが正本で、どれがそこから作る生成物か（手で直さない、作るコマンド）。3 つで見つかった                                            |
| 01 インストール      | 利用者が入れるものがない（サーバー、ブラウザで使うもの、社内の運用）。3 つで空になる。プラットフォームごとの配布の経路と署名もない |
| 06 システム仕様      | パラメータの表、状態遷移、設定と環境の組み合わせで決まる振る舞い、監視と排他。仕様と実装の進み具合（済み / 未）が混ざることもある  |
| 07 API 仕様書        | 使う側として取り込む版（ブランチ、ハッシュ）。外向けの定義と、内部のサービス間の手書きの契約の区別                                 |
| 08 DB 仕様書         | DB の代わりにスプレッドシートを使う場合（シートごとに書く人、列の分担、数式、保護、作り直し）                                       |
| 10 環境構築          | 任意だが、ある作業（コード生成など）では要る前提。OS ごとの手順は、手順の os とタブで表せるようになった                            |
| 11 環境変数          | 既定値、誰が使うか（アプリ、マイグレーション、デプロイ）、値の入手先（人に聞く）、ビルドに同梱されるか、秘密ではないが git に入れないもの |
| 12 開発者コマンド    | 危険度と対象の環境（本番に触るか）、ほかのコマンドをまとめて呼ぶもの、AI と人で許可が違うこと                                      |
| 13 インフラと環境    | ローカルの補助サービスとポート（差分計算用の DB、API ドキュメントの表示）、環境の非対称（開発環境から本物のアカウントに届く）、環境の違いがアプリの中の分岐で出ること |
| 14 デプロイとリリース | 自動か手動か、どこから実行するか（GUI、作業用の PC から本番へ）、CI がないこと                                                       |
| 15 費用              | 無料枠の上限、判断のしかた、払えばできることの値段                                                                                   |
| 09 ディレクトリ構成  | ディレクトリごとの読み書きの権限                                                                                                     |

## 3. 今の docv で受けられるもの

| 種類                     | 受け方                                                                                       |
| ------------------------ | -------------------------------------------------------------------------------------------- |
| 意思決定の記録           | 原本に今の決定と理由を書き、捨てた案は retire で archive に移す。ただし「更新しない記録」の運用とは考え方が違う |
| 未実装、未決、予定、計画 | 原本にタグ（未決、計画など）を付ける                                                         |
| コーディング規約         | 原本にタグ（規約）を付ける                                                                   |
| ドキュメントの運用ルール | docv 自身のルール（frontmatter、枠、タグ、retire）が受け持つ                                 |
| AI Agent 向けの指示      | docv の外（CLAUDE.md など）。docv desc はドキュメントのルールだけを渡す                       |

---

## 4. 枠を足すかどうか考えること

- 4 つのうち 3 つ以上で見つかり、docv の今の仕組みで受けられないのは、運用手順と障害対応、開発の進め方、テスト方針、外とのつながり
- 運用手順と障害対応は、手順の枠（requirements と steps）の形で書ける。「いつやるか（障害時、月次）」と「対象の環境」の項目があれば足りそう
- 正本と生成物の関係は、枠ではなく、07、08 などに共通の項目（正本のパス、作るコマンド、手で直さない）にする手がある
- 権限とアカウントは、環境変数の枠を広げるか、別の枠にするか
- 画面一覧は、以前「リンクするくらいがいい」とした。2 つで見つかったが、形がプロジェクトごとに違う
- 01 インストールが空になるプロジェクトが多い。利用者が入れるものがないときの書き方（「ブラウザで使う」と 1 行書くなど）を決める
