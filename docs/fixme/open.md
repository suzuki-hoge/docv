# 未決事項

docv の設計のうち、まだ決まっていないこと。決まったら答えを spec/ に書き、ここから消す。

---

## 1. HTML にどんな画面とセクションを置くか

試作の HTML を生成し、それを見ながら決める。候補は次のとおり。

- トップ（overview と、動かし方・費用・仕様などへの入口）
- 種類 × 話題のマップ
- 未来（plan、proposal、fixme）の一覧
- ファイル間のリンクの関係図

あわせて決めること。

- 費用を集計して見せるか。見せるなら、金額を frontmatter でどう持つか
- git の履歴から「最近の変更」を出すか。出すなら、docs をコミットする前と後で出力が変わらないようにする方法
- Mermaid などの図を描画するか

---

## 2. desc のルールファイルと spec をどう揃えるか

ルールファイルは、spec/concept.md、spec/kind.md、spec/writing.md を AI Agent 向けにまとめたもので、同じことを 2 か所に書くことになる。spec から生成するか、手で揃えて check で差を見るか。

---

## 3. retire のあとに章番号を振り直すか

振り直すと読みやすいが、章へのリンクのアンカーが変わる。

---

## 4. リンクのアンカーを check するか

GitHub が見出しからアンカーを作る規則（日本語を含む）に合わせる必要がある。

---

## 5. 違うマシンでも同じ JPG にするか

同じにするには、フォントを埋め込む必要がある。日本語のフォントはサイズが大きい。

---

## 6. CLI のメッセージとルールファイルを何語で書くか

日本語にするか、英語にするか、切り替えられるようにするか。

---

## 7. proposal と fixme を分けたままにするか

案があって検討しているものを proposal、決まっていないことを fixme としている。実際に使って分けにくければ、1 つにまとめる。

---

spec/check.md の語を試作のときに docs にかけて、誤検知と見逃しを見る。

## 11. dprint-plugin-markdown で決めた整形の形にできるか

表の列の幅を全角文字 2 文字分で数えるか、frontmatter をそのまま残すか、箇条書きと強調の記号を指定できるかを確かめる。できないものがあれば、その部分だけ docv が自分で整形する。

---

## 12. textlint の組み込みのプリセットで、docv の既定で切っておくルールはあるか

たとえば、箇条書きの文末に句点を求めるルールや、全角と半角の間にスペースを入れないことを求めるルールは、docs の書き方とぶつかりやすい。あわせて、textlint が frontmatter を本文として扱わないかを確かめる。

---

## 13. textlint の自動修正を docv から呼べるようにするか

`docv fmt` に含めるか、`docv check --fix` のような別の入口にするか、呼べないままにするか。
