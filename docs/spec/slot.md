# Slot

どのプロジェクトにも要るドキュメントを、docv が決めたミッションと形で書くファイルの規格。Slot を置く理由と HTML の全体は、Slot の「サービス仕様」（[`docv/service/service.md`](../../docv/service/service.md)）。

---

## 1. 置き場所と書き方

- Slot ファイルは、`docv.yaml` の `dir.slot`（既定は `docv`）に、`<まとまり>/<Slot>.<拡張子>` の名前で置く。まとまりのディレクトリは `service`（サービス仕様）、`system`（システム仕様）、`guide`（開発者向けガイド）、`operation`（運用）。`docs/` には Free ファイルを、`docv/` には Slot ファイルを置く
- 拡張子は Slot ごとに決まる。YAML の Slot は決まった項目で書き、md の Slot は中身の形を決めず、そのまま HTML に出す
- `docv/adr/` は ADR の置き場所で、Slot としては読まない（[`spec/adr.md`](adr.md)）
- Slot を置くかどうかは任意。プロジェクトに当てはまらない Slot は作らない（例: 利用者の手元に入れるものがなければ、インストールの Slot はいらない）。`index.html` には置いていない Slot のカードも並べ、グレーにしてリンクにしない
- Slot のミッションに当たる詳しいことも、Slot の中に書く。Free ファイルへのリンクで済ませない
- ファイルの中のパスは、すべてルートからの相対パスで書く。md の Slot の中のリンクは、ほかの Markdown と同じく、ファイルの場所からの相対パスで書く
- YAML の文字列の項目には Markdown を書ける
- `docv slot gen <slot>` で、Slot ファイルを決まったパスに作れる。YAML の Slot には項目のサンプルを書き、md の Slot は空のファイルを作る（`docv slot list` で一覧とミッションを出す）

## 2. 一覧

HTML には、この表の順に、まとまりごとに並べる。

| ファイル                      | Slot           | まとまり         | ミッション                                                     |
| ----------------------------- | -------------- | ---------------- | -------------------------------------------------------------- |
| `service/install.yaml`        | インストール   | サービス仕様     | 利用者がこれを入れる手順                                       |
| `service/service.md`          | サービス仕様   | サービス仕様     | これの目的、利用者、解決すること、部品の構成                   |
| `service/manual.md`           | 利用マニュアル | サービス仕様     | 利用者の使い方（CLI のコマンド、GUI の操作など）               |
| `service/words.yaml`          | 用語集         | サービス仕様     | このプロジェクトの言葉の意味                                   |
| `system/stack.yaml`           | 技術スタック   | システム仕様     | 作るのに使っている言語、ライブラリ、サービス                   |
| `system/system.md`            | システム仕様   | システム仕様     | システムの内部の動きと、従う決まり                             |
| `system/api.md`               | API 仕様書     | システム仕様     | API の一覧と、それぞれが受け取るものと返すもの                 |
| `system/db.md`                | DB 仕様書      | システム仕様     | 保存しているデータと、その保存先と形                           |
| `guide/directory-tree.yaml`   | ディレクトリ   | 開発者向けガイド | ディレクトリごとの役割                                         |
| `guide/setup.yaml`            | 環境構築       | 開発者向けガイド | 開発を始めるのに用意するものと、実行するコマンド               |
| `guide/env.yaml`              | 環境変数       | 開発者向けガイド | システムを動かすのに要る環境変数と、それぞれを設定している場所 |
| `guide/develop.yaml`          | 開発コマンド   | 開発者向けガイド | テストやビルドなど、開発者が実行するコマンド                   |
| `guide/doc-guide.md`          | Doc ガイド     | 開発者向けガイド | このプロジェクトのドキュメントの置き場所と書き方               |
| `operation/infrastructure.md` | インフラと環境 | 運用             | 環境（本番、ステージング、開発など）の一覧と、それぞれの用途   |
| `operation/deploy.md`         | デプロイ       | 運用             | 作ったものを環境に反映する手順                                 |
| `operation/release.md`        | リリース       | 運用             | 版の決め方と、利用者への届け方                                 |
| `operation/cost.yaml`         | 費用           | 運用             | かかっている費用と、費用を理由にやっていないこと               |

- Slot の名前に近いパスで置くと、check が slot-unknown で正しいパスを示す。たとえば、まとまりのディレクトリが違う `words.yaml`、番号を付けた `service/03-words.yaml`、拡張子が違う `service/service.yaml`
- 利用マニュアル（manual）と開発コマンド（develop）を分けるのは、使う人と目的が違うため。利用マニュアルは、リポジトリが CLI や GUI のときの、利用者向けの使い方
- サービス仕様には、これが何で、どんな部品からなるか（外から見た姿）を書く。システム仕様には、内部でどう動くかを書く
- インフラと環境には、ある環境だけでなく、ない環境も書く（例: ステージングと本番があり、開発サーバーはない）
- デプロイは環境に反映すること、リリースは利用者に届けることで、どちらかしかないプロジェクトもある（例: サーバーを持たない CLI はリリースだけ）。どちらも、環境ごとの違い、承認、切り戻しなど、手順の形に収まらないことを書くので md にする

## 3. YAML の Slot の項目

<details>
<summary>手順の Slot（インストール、環境構築、開発コマンド）</summary>

| 項目           | 中身                                                                    |
| -------------- | ----------------------------------------------------------------------- |
| `requirements` | 前提とされるもの。`name`、`version`、`purpose`、`url`                   |
| `steps`        | 手順の配列。`id`、`name`、`items`。`items` は `os` と `markdown` を持つ |

- `id` は手順ごとに重ねない
- `markdown` は、その手順の中身（コマンド、説明など）を Markdown で書く
- `items` が 1 つなら、配列にしなくてよい。HTML ではタブにしない
- `items` が複数あるときは、HTML で `os` ごとのタブにする。どの `item` にも `os` を書き、`os` は重ねない。タブは書いた順に並べる。`os` は windows、macos、linux など

````yaml
steps:
  - id: binary
    name: バイナリを取る
    items:
      - os: windows
        markdown: リリースのページから zip を取り、展開する
      - os: macos
        markdown: |
          ```sh
          curl -L https://example.com/example-macos.tar.gz | tar xz
          ```
  - id: cargo
    name: ソースから入れる
    items:
      markdown: "`cargo install example`"
````

</details>

<details>
<summary>用語集、技術スタック、ディレクトリ</summary>

| Slot           | 項目      | 中身                                                                                                        |
| -------------- | --------- | ----------------------------------------------------------------------------------------------------------- |
| words          | `groups`  | 用語のまとまりの配列。`name` と `items`。`items` は `ja`、`en`、`desc`。`ja` と `en` はどちらかがあればよい |
| stack          | `stack`   | 層の配列。`group`、`image`（任意。図があれば出す）、`items`                                                 |
|                |           | `items` は `name`、`version`、`purpose`、`url`                                                              |
| directory-tree | `entries` | `path` と `description` の配列。パスの親子でツリーにし、兄弟は書いた順に並べる                              |

</details>

<details>
<summary>環境変数、費用</summary>

| Slot | 項目             | 中身                                                                |
| ---- | ---------------- | ------------------------------------------------------------------- |
| env  | `envs`           | `key`、`desc`、`secret`、`local_from`、`release_from` の配列        |
| cost | `accepted_items` | 費用をかけて使っているもの。`name`、`desc`、`monthly`、`ref` の配列 |
|      | `rejected_items` | 費用を理由にやっていないこと。形は `accepted_items` と同じ          |

- 環境変数の `secret` は、秘密の値か。`local_from` と `release_from` には、どこで設定しているかを書く
  - `local_from`: ローカル環境（Docker Compose、`.env` など）
  - `release_from`: ステージングや本番（ECS のタスク定義、SSM など）
- 費用の `monthly` は 1 か月あたりの金額で、数でも文字列（「3 ドル」など）でもよい。予算が変われば、`accepted_items` と `rejected_items` の間で項目を移す

</details>

- 項目にない文章は、YAML の Slot には書けない。Free ファイルに書いてリンクする
- YAML の Slot には、項目の型と意味を書いたスキーマ（JSON Schema）がある。`docv slot schema <slot>` で出す。元のファイルは `assets/schema/<ID>.schema.json` で、`docs/schema/` に写しを置く
- `docv slot gen` は、YAML の Slot の 1 行目に、yaml-language-server の書式でスキーマの URL を書く。URL は、実行した CLI の版のタグの `assets/schema/` を指す。エディタで項目の補完と検証が効く

## 4. md の Slot

- 中身の形は決めない。YAML front matter は要らない
- `docv slot gen` は空のファイルを作り、中身の形は自由だと表示する。Doc ガイド（`guide/doc-guide.md`）だけは、docv が勧めるガイドラインを書いた雛形を作る。作った雛形はプロジェクトのもので、自由に直してよい。docv の版を上げても書き換えない
- HTML では、最初の h1 を除き、いちばん浅い見出しが h2 になるように段を付け直して出す
- 見出しには、Free ファイルのページと同じく、GitHub と同じ形のアンカーを付ける。`[docv init](#docv-init)` のようなページ内リンクが HTML でも GitHub でも飛べる
- md の Slot のページは JPG にしない。md は GitHub でそのままプレビューできるため

## 5. check

| ID                | 内容                                                                                                               |
| ----------------- | ------------------------------------------------------------------------------------------------------------------ |
| slot-unknown      | Slot のディレクトリに、Slot の名前でないファイルがある                                                             |
| slot-invalid      | YAML の Slot の形に合わない。知らない項目、手順の `id` の重なり、`os` のない `item`、`ja` も `en` もない用語も含む |
| slot-path-missing | パスの先がない                                                                                                     |

- directory-tree の `path` の先がなくなったら、ディレクトリの Slot が実装からずれたということ。実装とずれたことに気づけるのは、ここだけ

## 6. HTML での見せ方

- Slot は 1 つずつ独立したページ（`<まとまり>/<Slot>.html`）にする。`index.html`（プロジェクト概要）には、まとまりの見出しの下に、「一覧」の章の順で、すべての Slot のカードを横に並べる。画面の幅に収まらなければ折り返す。紙面を縦に使いすぎず、画像にしてもすべてのカードが写るため。置いていない Slot のカードは、グレーにしてリンクにしない。どのミッションのドキュメントがないかを見せるため。カードの幅は固定し、画面の幅に合わせない。幅は、いちばん長い Slot の名前（7 文字）が折り返さない大きさ
- Slot のカードと、Slot のページの見出しには、Slot ごとのアイコンを付ける。アイコンは、docv が Slot ごとに持つ線画の SVG で、外部の素材を使わない
- Slot のページには、Slot の名前の見出しを出す。「一覧」の章のミッションは HTML には出さない。ミッションは、AI Agent がどの Slot に書くかを決める手がかりにする
- 折りたたみは使わない。`details` も、Markdown の中の `<details>` も、開いて出す。画像にしても、すべての中身が読めるようにするため
- 開閉するのは、OS ごとの手順のタブだけ。JPG では、すべての OS の手順を並べて写す
- 用語集は、まとまりごとに `name` を h2 にし、`items` を「日本語 | 英語 | 意味」の表にする
- 見た目に凝らない。見出し、段落、箇条書き、表だけで出す
- ディレクトリは、1 つの表に 1 段だけを「名前 | 説明」で出し、入れ子は表を分けて出す。いちばん上の段の表を先に置き、下の段を持つディレクトリごとに、そのパスの h2 と、その下の 1 段の表を後ろに並べる。並びは、親の次にその子の順。下の段を持つディレクトリの名前は、その表へのページ内リンクにする。表の名前はコードの書式にし、h2 のパスはコードの書式にしない。名前の列の幅は、表どうしで揃える。入れ子を折りたたみで見せないのは、画像にしても読めるようにするため。`entries` に書いていない途中のディレクトリは、説明なしで出す
- 見出しは、ページの先頭の h1（Slot の名前）が 1 つだけで、その下に h2 を並べる。段は飛ばさない（h1 の次に h3 や h4 を置かない）
  - Markdown（md の Slot、`details`、手順の中身）の見出しは、置く場所に合わせて段を付け直す。md の Slot は h2 から、`details` と手順の中身は h3 から
- 手順（インストール、環境構築）は、「手順」の h2 の下に番号付きで並べる
- 開発コマンドは、順番のない項目なので番号を付けない。先頭に目次（項目へのページ内リンク）を置き、各項目を h2 で始める
