# 書き方

docv で管理する Free ファイル（`docs/` の Markdown）を書く・直すときのルール。人間と AI Agent の両方が従う。

---

## 1. 書く前に決めること

1. 書くべき変更か
   - 振る舞い、手順、設定、費用、規約が変わったときだけ書く
   - コードを変えただけなら書かない。「書かない」も正しい結論として扱う
2. Slot ファイルか、Free ファイルか
   - インストール、サービス仕様、利用マニュアルのように、Slot がある問いなら Slot に書く（[`spec/slot.md`](../../spec/slot.md) の 2 章）
   - それ以外は Free ファイルに書く
3. どのファイルか
   - 各ファイルの YAML front matter の `mission` を見て、問いに収まるファイルを選ぶ
   - 収まるファイルがなければ、`docs/` に新しく作る

---

## 2. 何をどこに書くか

| 書く内容                                                                 | 書く場所                                                                                          |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| どのプロジェクトにもある問いへの答え（サービス仕様、利用マニュアルなど） | Slot                                                                                              |
| 決まったこと                                                             | Free ファイル。前の内容を直接書き換える                                                           |
| 今の状態の理由                                                           | Free ファイルに 1〜2 行。細かい理由は `<details>` に入れる                                        |
| 決めた経緯、選ばなかった案                                               | ADR（[`spec/adr.md`](../../spec/adr.md)）。決定 1 つを 1 つのファイルにし、決めた後は書き換えない |
| やったこと                                                               | PR とコミットメッセージ。ドキュメントには書かない                                                 |
| 実装状態、コードの改善点                                                 | 書かない。必要なら Issue にする                                                                   |
| まとまっていない意思決定、後で見る可能性のあるメモ                       | 管理外のファイル（`ignore` に入れたディレクトリなど）。ほかのドキュメントからリンクも言及もしない |

- Slot の問いに答える詳しいことも、Slot の中に書く。Free ファイルへのリンクで済ませない
- Slot ファイルと Free ファイルに同じことを書かない。Free ファイルに既にある章を Slot に出したいときは、Slot の `include` で埋め込む

---

## 3. YAML front matter

| key       | 必須 | 中身                             |
| --------- | ---- | -------------------------------- |
| `mission` | 必須 | このファイルが答えること（1 文） |
| `tags`    | 任意 | タグの配列（4 章）               |

```yaml
---
mission: 注文の処理は、どの注文をいつ確定し、失敗したときにどう扱うか
tags: [仕様, 注文]
---
```

- ファイルごとの設定は、すべて YAML front matter に書き、`docv.yaml` には書かない。ファイルを動かしても設定がずれず、AI Agent はファイルを読むだけで、そのファイルの扱いが分かる
- `docv.yaml` の `overrides` で `mission: optional` にしたパスでは、`mission` を書かなくてよい（[`spec/config.md`](../../spec/config.md) の 3 章）
- docv が知らない key は、そのまま残し、check もしない。作成者の記録（`created` / `updated` など）のように、プロジェクトの規約で決めた key を書いてよい

### `mission`

- 1 文で、このファイルが答えることを書く。疑問の形（〜は何か、どう〜か）にすると、範囲が決まりやすい
- ファイルの中身は、この `mission` への答えだけにする
- HTML は、`mission` をファイルの説明として表示する。AI Agent は、`mission` を見て読むファイルを選ぶ。タイトルとは別に、「このファイルを読むと何が分かるか」が伝わるように書く

| 良い                                                         | 悪い                                         |
| ------------------------------------------------------------ | -------------------------------------------- |
| 注文の処理は、どの注文をいつ確定し、失敗したときにどう扱うか | 注文の処理について（範囲が決まらない）       |
| 決済サービスに何にいくらかかり、費用を理由に何を決めているか | 費用まわり全般（どこまで書くかが決まらない） |

### YAML front matter を書けないファイル

- `README.md` のように YAML front matter を書きたくないファイルは、管理対象にしない。GitHub は YAML front matter を表として表示するため
- `README.md` の章を HTML に出したいときは、Slot の `include` で埋め込む（[`spec/slot.md`](../../spec/slot.md) の 3 章）

## 4. タグ

- Free ファイルの分類は、YAML front matter の `tags` に書くタグで行う。1 つのファイルにいくつでも付けられる。ディレクトリと違い、1 つのファイルが複数の分類に入れる
- docv はタグの意味を決めない。どんなタグを使うかは、プロジェクトが決める
- `docv.yaml` に `tags`（タグの一覧）を書いたときだけ、YAML front matter の `tags` をその中に限る。書かなければ、どんなタグでも付けられる

### タグに付けるルール

`docv.yaml` の `lint.tags` に、タグごとにルールを書く。そのタグを持つファイルにだけ、ルールをかける。1 つのファイルが複数のタグを持てば、それぞれのタグのルールをすべてかける。

```yaml
lint:
  tags:
    仕様: [no-past-wording]
    計画: [no-done-task]
```

| ルール          | かけること                                                                   |
| --------------- | ---------------------------------------------------------------------------- |
| no-past-wording | 過去や実装状態の言い回しを warn にする（10 章の past-wording、past-heading） |
| no-done-task    | 終わったタスク（`- [x]`）を warn にする                                      |

### 推奨するタグ

今の姿だけを書く考え方を取り入れたいプロジェクトには、次のタグとルールを推奨する。

| タグ | 書くこと                                     | ルール          |
| ---- | -------------------------------------------- | --------------- |
| 仕様 | 振る舞い、データの意味、境界、今の状態の理由 | no-past-wording |
| 手順 | コマンド、手順、うまくいかないときの対処     | no-past-wording |
| 規約 | 書き方や守ること                             | no-past-wording |

- 決めた経緯と選ばなかった案は、タグではなく ADR に残す
- サービス仕様、技術スタック、利用マニュアルのように、どのプロジェクトにもある問いは、タグを付けた Free ファイルではなく Slot ファイルに書く

---

## 5. 書き換える

- Free ファイルは、前の内容を直接書き換える。後ろに足していかない
- 古い内容は消す。なぜ変えたか、何と比べて選んだかを残したいときは、ADR を書く
- `〜に変更した`、`以前は`、`未実装` のような言い回しは書かない。no-past-wording のルールを付けたタグのファイルでは、check が警告する

---

## 6. 要点と詳細を分ける

- Free ファイルの本文には要点を書き、細かい理由、例外、例は `<details>` に入れる
- GitHub では `<details>` は折りたたんで表示される。読む人は、要点だけを読んで、必要なときに開ける。HTML のページでは、画像にしても読めるように開いて出す

```markdown
- 注文は、決済が通った時点で確定する

<details>
<summary>決済の前に確定しない理由</summary>

在庫を先に押さえると、決済に失敗したときに戻す処理が要る。

</details>
```

---

## 7. 範囲を守る

- 問いに収まらない内容を足さない。別のファイルに書くか、新しいファイルを作る
- 内容を収めるために、問いを広げない
- 大きさは文字数ではなく、問いで決める。問いに対してファイルが大きくなったら、問いを分け、ファイルも分ける

---

## 8. 読み書きの権限

| 対象                                       | 人間             | AI Agent                                                                  |
| ------------------------------------------ | ---------------- | ------------------------------------------------------------------------- |
| Slot ファイル、Free ファイル               | 読む、書く       | 読む、書く                                                                |
| ADR                                        | 必要なときに読む | 決めた理由を聞かれたときだけ読む。決めた後は書き換えず、新しい ADR を足す |
| docv build-html と docv build-image の出力 | 見る             | 読まない、書かない                                                        |
| 管理外のファイル                           | 制限しない       | 制限しない                                                                |

---

## 9. 書式

- docv が決めるのは、YAML front matter（3 章）と、Slot の形（[`spec/slot.md`](../../spec/slot.md)）だけ
- 章番号、文体、強調の使い方などは、プロジェクトが決めて規約に書く
- そのうち機械で確かめられるものは、`docv.yaml` で書式の規則と textlint を使うように設定して、check で確かめる（[`spec/config.md`](../../spec/config.md) の 5 章と 6 章）
- 空行や表の余白は、手で揃えずに `docv fix` で整形する

---

## 10. check のルール

`docv check` が Free ファイルで確かめるルール。Slot のルールは [`spec/slot.md`](../../spec/slot.md) の 5 章、ADR のルールは [`spec/adr.md`](../../spec/adr.md) の 3 章に書く。`docv.yaml` で使うと決めたときだけ確かめるもの（書式の規則、整形、textlint）は [`spec/config.md`](../../spec/config.md) に書く。

### YAML front matter

| ID                  | 強さ  | 内容                                                       |
| ------------------- | ----- | ---------------------------------------------------------- |
| frontmatter-invalid | error | YAML front matter が読めない。`mission`、`tags` の型が違う |
| mission-missing     | error | `mission` がない                                           |
| mission-multiline   | error | `mission` が複数行                                         |
| tag-unknown         | error | `docv.yaml` に `tags` を書いたとき、そこにないタグがある   |

- `docv.yaml` の `overrides` で `mission: optional` にしたパスでは、mission-missing を出さない

### 構造とリンク

| ID          | 強さ  | 内容                                           |
| ----------- | ----- | ---------------------------------------------- |
| title-count | error | h1 が 1 つでない                               |
| link-broken | error | ルートの中を指す相対リンクの先にファイルがない |

- リンクのアンカー（`#` 以降）は確かめない

### タグに付けたルール

`lint.tags` でタグに付けたときだけ、そのタグを持つファイルで確かめる。コードブロックとインラインコードの中は見ない。

| ID           | 強さ | タグのルール    | 内容                                   |
| ------------ | ---- | --------------- | -------------------------------------- |
| past-wording | warn | no-past-wording | 本文に、過去や実装状態の言い回しがある |
| past-heading | warn | no-past-wording | 見出しに、過去を扱う語がある           |
| done-task    | warn | no-done-task    | 終わったタスク（`- [x]`）が残っている  |

既定の語は次のとおり。`docv.yaml` の `lint.words.add` は past-wording に語を足し、`lint.words.remove` は両方から語を外す。語は大文字と小文字を区別し、部分一致で探す。

| ルール       | 既定の語                                                                                                                                                                        |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| past-wording | `以前は`、`従来は`、`旧仕様`、`旧方式`、`に変更した`、`に変更しました`、`を廃止した`、`を廃止しました`、`未実装`、`実装予定`、`実装済み`、`今後は`、`将来的に`、`TODO`、`FIXME` |
| past-heading | `変更履歴`、`更新履歴`、`経緯`、`廃案`、`不採用`、`未実装`、`今後の予定`                                                                                                        |
