docv/pdr/guide-slots.md

開発者向けガイドに、アーキテクチャ、設計・実装、テスト方針の Slot を足す

背景

開発者向けガイドには、環境構築、開発コマンド、環境変数、Doc ガイドがあった。開発者がコードを書く前に知っておく方針を書く Slot はなかった。ある程度の大きさのサービスでは、次のどれもが要る。

  • システム全体の方式（部品の分け方、通信の方式、非同期処理の実現方法）
  • コードの決まり（フレームワークの使い方、ディレクトリやコーディングの決まり）
  • テストの方針

Slot がないので Free ファイルへ書くしかなく、置き場所と書き方がプロジェクトごとにばらつく。

Doc ガイドの雛形では、コードを読めば分かる実装は書かないと決めていて、コードの決まりをどこに書くかが決まっていなかった。

決めたこと

開発者向けガイドに、次の 3 つの md の Slot を足す。どれもページに分けられる。

Slotファイルミッション
アーキテクチャguide/architecture.mdシステム全体で採る方式と決まり（部品の分け方、通信の方式、非同期処理の実現方法など）
設計・実装guide/design.mdコードを書くときに従う決まり（フレームワークの使い方、ディレクトリやコーディングの決まりなど）
テスト方針guide/testing.mdテストの範囲と方法（自動テストの範囲、E2E テスト、手動テストについてなど）

開発者向けガイドは、環境構築、開発コマンド、アーキテクチャ、設計・実装、テスト方針、環境変数、Doc ガイドの順に並べる。

  • アーキテクチャのミッションでは、「サービスの分け方」ではなく「部品の分け方」と書く。docv では、画面、サーバ、バッチなどを部品と呼び、サービスは外から見た製品を指す（サービス概要、サービス仕様）
  • 技術スタックは、使っている製品やライブラリの名前を一覧で見るための Slot のまま残す。方式は、アーキテクチャに書く
  • 設計・実装には、コードを読んでも、守るべき決まりか、たまたまそうなっているかが分からないことを書く。今のコードの作り（実装）は、これまでどおり書かない
  • テスト方針には、何をどのテストで確かめるかを書く。テストを実行するコマンドは、開発コマンドに書く
  • Doc ガイドの雛形の言葉の使い分けに、アーキテクチャと実装の決まりを足す。これまでアーキテクチャと呼んでいた部品の構成は、システム構成と呼び、システム概要に書く

結果

  • 方式、コードの決まり、テストの方針に、どのプロジェクトでも同じ置き場所ができる。AI Agent は、ミッションで書く Slot を決められる
  • Free ファイルに書いていた方式や決まりは、Slot に移せる。移すかどうかは、プロジェクトが選ぶ
  • アーキテクチャは、システム概要やシステム仕様と書く場所が近い。境目は Slot の規格の注に書く

見直す条件

  • 3 つの Slot のどれに書くか、またはシステム概要やシステム仕様に書くかで迷う記述が、繰り返し出たとき

選ばなかった案

案選ばなかった理由
方式や決まりは、Free ファイルに任せる置き場所がプロジェクトごとに違い、AI Agent がミッションで書く場所を決められない
技術スタックに、方式を書く項目を足す技術スタックは名前を一覧で見るためのもので、方式の説明を足すと一覧が読みにくくなる
