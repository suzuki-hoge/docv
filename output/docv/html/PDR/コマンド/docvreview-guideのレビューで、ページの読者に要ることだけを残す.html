docv/pdr/review-by-reader.md

docv review-guide のレビューで、ページの読者に要ることだけを残す

背景

docv review-guide のレビューは、ドキュメントの今の姿と決まり、その理由、境目（やらないこと）を残し、それ以外を除くことを目的にしていた。

この目的では、人間が読むページに入り込んだ、コードを直す人に向けた注意を除けなかった。たとえば、デプロイ手順のページに「デプロイの仕組みを直すときの決まり」の章ができる。決まりの理由、境目、実装の決まり、ADR への参照は、削るべきでないものとして守られていた。

YAML front matter に、読む人、読む場面、書かないものの項目を足しても防げない。どのページでも、同じ決まりの言い直しになるためである。

レビューは、ドキュメントだけを読んで行っていた。コードのコメントやエージェントの指示ファイルと同じことが書いてあっても、気づけなかった。手順のページに、戻せないことや、戻している間の振る舞いが書いていなくても、指摘する観点がなかった。

決めたこと

レビューでは、どのページも、そのページの読者に要ることだけを残す。読者に要るのは、読者の行動を変えることか、読者が自分では知れないこと。

判断の基準（何を書き、何を書かないか）Doc ガイドプロジェクトで直せる

読者で見る

  • 読者が自分で知れること（使えば分かること、一般的な知識、コードや生成物やエージェントの指示ファイルの写し）は消す
  • 読者の違うこと（その事柄を変える人に向けた決まりや理由）は、ドキュメントの外（その値の隣のコメントなど）へ移す
  • 決まりの理由、境目、実装の決まりは、読者に要るときだけ、削るべきでないものとして守る
  • Slot と Free ファイルの本文にある、ADR と PDR の案内を指摘する
  • ほかの Slot の案内は、ページの冒頭に並べたものだけを指摘する

手順

  • 初めに、ドキュメントだけで見るか、コードやインフラの定義も調べるかを人間に確かめる
    • 頼むときに言われていれば、聞かない
  • 手順のページは読者としてなぞり、戻せないこと、戻している間の振る舞い、気づけないことが書いてあるかを見る
    • 足りなければ、書き足さずに、問いとして人間に出す
  • 直すときは、消す・移すを先にし、割る・畳むを後にする
    • 消せるものを消すと、割るものや畳むものはほとんど残らないため
  • Slot と Free ファイルの一覧は、docv review-guide では出さず、docv list を実行させる
    • 同じ一覧を、2 つのコマンドで作らないため

前の決定から変えないこと

  • review-guide は指摘を出さない
    • 指摘するのは、出力を受け取った AI Agent である
  • 手順と Doc ガイドが食い違うときは、Doc ガイドに従う
    • 基準をプロジェクトで調整できるようにするため
  • Doc ガイドにあって観点にない基準も、レビューで確かめる
  • レビューの対象は Slot と Free ファイルにし、ADR と PDR は対象にしない
    • 書き換えない記録で、ふさわしいかは書くときに決めたほうが早いため
  • 一覧に出す ADR と PDR は、打ち消されていないものだけにする
    • 打ち消された決定を今の決定として読み、誤った食い違いを指摘させないため
  • 決定との矛盾は揃えず、人間に確かめる
    • 決定を変えるには、新しい ADR か PDR が要るため
  • 観点ごとに直し方を決め、AI Agent はその中から選ぶ
    • 決めていないと、AI Agent は書き足す直し方を選びがちなため
  • ドキュメントのどこにも書いていない情報は、書き足さない
    • 例外は、決定との矛盾で新しい ADR か PDR を書くことだけ
  • レビューの結果はファイルに書かず、直すのは人間が選んでからにする
    • レビューの報告が、新しい作業の報告として溜まらないようにするため
  • 人間が「このままでいい」と答えた指摘は、その判断を一般化した 1 行を、Doc ガイドに足す案として示す
    • 観点を丸ごと外す 1 行にはしない
  • 一覧に見出しと行数は出さない
    • 対象はすべて読ませ、大きさでは判断させないため
  • HTML のサイドバーに Review Guide のページを置き、review-guide と同じ手順を出す。一覧は出さない
    • build した時点の一覧はずれていき、HTML を git で管理していると、ファイルを足すたびに差分が出るため
  • Doc ガイドの雛形には、手順は書かず、レビューを提案するきっかけだけを書く

結果

  • レビューで、人間が読むページから、コードを直す人に向けた注意や、コードとコメントの写しが消える
    • 消えた理由や決まりは、その値の隣のコメントなど、変える人が読む場所へ移る
  • コードやインフラの定義も調べるレビューは、ドキュメントだけのレビューより時間がかかる
  • 手順のページの足りないことは、問いとして出るだけで、答えて書き足すかは人間が決める
  • 読者に要るかの判断は AI Agent に任せるので、レビューごとにぶれる
    • 人間が断った指摘は、Doc ガイドに足した 1 行で、次のレビューでは出なくなる
  • すでに Doc ガイドを作ったプロジェクトには、雛形に足した基準が入らない
    • Doc ガイドは、docv の版を上げても書き換えないため
    • 版を上げるときに、update-guide で案内する

見直す条件

  • 「このままでいい」と答えて Doc ガイドに足した 1 行が、読者の違う記述か、自分で知れる記述の観点に当たるものだけで 5 行を超えたとき
    • 読者で見る基準が、プロジェクトの考えと合っていないという合図になる
  • review-guide の出力を書き写し、観点を直したファイルをプロジェクトに置く利用者が出たとき
    • 観点もプロジェクトで調整したいという合図になる

選ばなかった案

案選ばなかった理由
YAML front matter に、読む人、読む場面、書かないものの項目を足すどのページでも、同じ決まりの言い直しになる
調べる範囲を選ぶオプション（--full-scan など）を作る人間に聞く文 1 つで済み、HTML の Review Guide のページの手順と同じものを出せる
形の指標（入れ子の深さ、項目の文の数など）を機械で測って指摘する形の崩れは症状で、消せるものを消すと、ほとんど残らない
手順のページに足りないことを、AI Agent が書き足すドキュメントのどこにも書いていない情報を、推し量って書くことになる
今までどおり、理由、境目、実装の決まりを、読者を問わず削るべきでないものにする人間が読むページに、コードを直す人に向けた注意が残り続ける
