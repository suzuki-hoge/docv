Doc ガイド

このプロジェクトのドキュメントを書く・直すときの方針。人間と AI Agent の両方が従う。

本ファイルは docv slot gen doc-guide が作った雛形で、プロジェクトに合わせて調整し利用する。

docv desc で定義されるルール、設定、ガイドラインのうち、このページはガイドラインについての指示ファイルである。

言葉の使い分け

docv の文脈においては、あいまいな「仕様」という言葉を避け次のように定義している。どのファイルになにを書くべきかの拠り所にすること。

言葉指すもの書く場所
サービス説明docv をなにも知らない利用者へ伝える最初の説明サービス概要
サービス仕様外から見た機能、振る舞い、決まり。実装をそっくり差し替えても変わらないこと
利用者、AI Agent、開発者が読む		要点はサービス仕様の 1 ページ目（docv desc）
詳しいことは 2 ページ目以降
アーキテクチャ部品（CLI、リポジトリのドキュメント、textlint、Chrome、出力など）の構成と役割、部品の間の流れ、どの処理をどの部品で行うか
開発者が判断を下すときに読む		全体像はシステム概要。SVG で描く
部品ごとの詳しいことはシステム仕様
サービスエラー利用者が書いたドキュメントや渡した引数が原因で起きるエラー
例: check の指摘、docv.yaml の誤り、終了コード		サービス仕様の 2 ページ目以降
システムエラー環境や外の道具が原因で起きるエラーと、その扱い
例: Chrome が見つからない、Chrome とのやりとりが途切れる		システム仕様
実装1 つの部品の中のことで、コードを読めば分かること（関数やモジュールの分け方、処理の手順、ライブラリの使い方）書かない
原則として必要とするのは AI Agent であり、それにとってはコードから自明であるため
設計何かを判断し決めること。ドキュメントの種類ではない決めたいことは docs/tmp/ や GitHub Issue
決めた結果はミッションに沿うファイル
経緯や廃案は ADR

サービス仕様とシステム仕様は、複数ページに分割できる。明確な分割点は docv では指定しないが、およそ次のような観点でページが肥大化しすぎないよう分割するといい。

  • 読み手の違う情報がページに混在している
  • 読むタイミングの違う情報がページに混在している
  • 異なるコンポーネントや異なる機能の情報がページに混在している

サービス仕様の 1 ページ目は、docv desc と同じ desc.md（assets/desc.md へのシンボリックリンク）にする。docv desc と一致させるため、このページは 1 ファイルのまま保ち、AI Agent が最初に読む要点だけを書く。詳しいことは 2 ページ目以降に書く。

書き分けの例

種類サービス仕様システム仕様
出力HTML のページの作りと、毎回同じ出力にする決まりChrome を動かして JPG を撮る流れ
エラーcheck の指摘と終了コード外の道具が見つからないときや、やりとりが途切れたとき
スキーマYAML の Slot と docv.yaml の項目スキーマを埋め込み、版のタグの URL で公開すること
外の道具textlint で確かめる項目と、使うかどうかの設定どのコマンドが、どの道具を、いつ呼ぶか

望ましいドキュメント

  • 概要と詳細が適切に分類されている
    • 概要は要点がまとまっていて、詳細は <details> で折りたたみ必要なときのみ視認できるようになっている
  • 現在の情報が整理されている
  • 用語集の単語に沿って書かれている
  • 事実と予定・課題管理を混ぜない

望ましくないドキュメント

  • mission の示す内容が一意になっていない / ひとつのファイルに複数の内容を混ぜている
  • 過去の情報がすべて羅列されている → 今現在知らなくていいことは随時削除し、必要な経緯は ADR に移す
  • 同じ内容が複数の箇所に書いてある
  • 実装が書いてあり、コードを変えるたびに直す必要がある
  • Slot のミッションに当たる内容が、Free ファイルに置かれている
  • コードの行番号やドキュメントの章番号など、頻繁に変更される情報に依存している

タグ

HTML 閲覧しやすくするため、Free ファイルにはタグをつける。

タグ書くこと
スキーマdocv.yaml と YAML の Slot の JSON Schema の写し（docs/schema/）

AI Agent への指示

  • セッション開始時に docv desc を実行し、本ファイルの指示に従いドキュメント管理をすること
  • Slot ファイルのスキーマは docv slot 系コマンドで確認すること
  • ドキュメント変更時は docv fix を通すこと
  • ドキュメントを書き足すときは、増えた情報を適切な量で反映すること
  • 実装は、指示がない限り書かないこと
  • Free ファイルを足す前に、その mission がどれかの Slot のミッションに当たらないかを確かめること。当たるなら、その Slot に書き、長くなるならページに分けること
  • Free ファイルに spec/ や architecture/ のような、Slot の代わりになるディレクトリができそうになったら、Slot のページ（タブ）の分け方を見直すこと
  • 既存の文書を Slot に移すときは、ミッションに当たらない記述を、ほかの Slot、Free ファイル、ADR に分けること。実装は移さないこと
  • 変わった情報は原則として上書きし、古くなった情報は原則として抹消すること
  • ADR は加筆の指示があるまで作成せず、必要と思われる状況では作成提案にとどめること
  • 検討中の項目、メモ、課題などを管理する場合は、正式ドキュメントとは分けて管理すること
    • タグや docv.yaml の ignore を活用すること
  • アスキーアートを用いたいときは、まず SVG で作図すること
