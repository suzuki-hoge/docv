Doc ガイド

人間と AI Agent の両方が、このページに従う。

本ファイルは docv gen doc-guide が作った雛形で、プロジェクトに合わせて調整し利用する。

docv desc で定義されるルール、設定、ガイドラインのうち、このページはガイドラインについての指示ファイルである。

書くか書かないか

書くのは、読者が困る前に、自分では知れないことだけ。読者は、次の手段なら自分で知れる。

知る手段中身
知っている一般的な知識。読者が AI Agent なら、なおさら知っている
読むコード、設定、生成物、テスト名、手順の並び
探す置き場所が docv で決まっているもの（ADR、PDR、用語集）
使う動かすと、製品、スクリプト、検証器、リンタが知らせてくれる
書くもの中身
入口何があり、どこから始めて、どこを読めばいいか
先に言えよ使って知ったのでは遅いこと（戻せない、ほかの人に影響する、時間やお金を大きく失う）
守らなくても何も起きず、あとで困ること
なぜ方針、背景、やらないと決めたこと。読者の行動を変えるものだけ
  • 迷ったら、「書かなかったら誰が、いつ、どう困るか」と問う
  • 消しすぎに気をつける
    • 「使えば分かる」は、失敗して知らせてくれるときだけ成り立つ
      • 同じことを重ねて確かめるテストは、何も知らせない
    • 一般的な方針の言い直しは消すが、具体にすると情報が増えるもの（何を期待値の出どころにし、何を表の軸にするか）は残す
      • 見分け方は、消したあと、一般的な方針だけから組み立て直せるか
    • 一般的な知識でも、仕様を閉じるのに要る値（式の定数など）は、畳んで残す
  • 道具（リンタ、スキル、検証器）で保証していることは、「X で検証している」くらいに書き、項目を並べない
    • 知りたければ、道具を見る
  • 近くのコードを読んで真似れば済むもの（テスト用の部品の一覧など）は書かない
    • 足りなければ、コードとコメントを直す
  • 今のコードの作り（関数やモジュールの分け方、処理の手順）は、コードを読めば分かるので書かない
  • 実装の決まり（コードを書くときに従う決まり）は、コード全体にかかり、コメントを置く 1 か所がないものだけを、設計・実装に書く
    • 1 か所に置けるものは、そのコードのコメントに書く

どこに何を書くか

ドキュメントの外も、正式な置き場所にする。

書く内容書く場所

  • 仕様は、実装の状態（未実装、止めている）にかかわらず、あるべき姿として書く

言葉の使い分け

docv の文脈においては、あいまいな「仕様」という言葉を避け次のように定義している。どのファイルになにを書くべきかの拠り所にすること。

言葉指すもの書く場所
サービス説明docv をなにも知らない利用者へ伝える最初の説明サービス概要
サービス仕様外から見た機能、振る舞い、決まり。実装をそっくり差し替えても変わらないこと
利用者、AI Agent、開発者が読む		要点はサービス仕様の 1 ページ目（docv desc）
詳しいことは 2 ページ目以降
システム構成部品（CLI、リポジトリのドキュメント、textlint、git、出力など）の構成と役割、部品の間の流れ、どの処理をどの部品で行うか
開発者が判断を下すときに読む		全体像はシステム概要。SVG で描く
部品ごとの詳しいことはシステム仕様
アーキテクチャシステム全体で採る方式と決まり（部品の分け方、通信の方式、非同期処理の実現方法など）
部品を足したり、つなぎ方を変えたりするときに読む		アーキテクチャ
その方式を選んだ理由は ADR
サービスエラー利用者が書いたドキュメントや渡した引数が原因で起きるエラー
例: check の指摘、docv.yaml の誤り、終了コード		サービス仕様の 2 ページ目以降
システムエラー環境や外の道具が原因で起きるエラーと、その扱い
例: textlint に要る Node.js が見つからない、ルートが git の管理下にない		システム仕様
設計何かを判断し決めること。ドキュメントの種類ではない決めたいことは docv/free/plan/
決めた結果はミッションに沿うファイル
経緯や廃案は ADR か PDR

サービス仕様、システム仕様、開発コマンド、アーキテクチャ、設計・実装、テスト方針、インフラと環境は、複数ページに分割できる。明確な分割点は docv では指定しないが、およそ次のような観点でページが肥大化しすぎないよう分割するといい。

  • 読み手の違う情報がページに混在している
  • 読むタイミングの違う情報がページに混在している
  • 異なるコンポーネントや異なる機能の情報がページに混在している

逆に、読み手、読むタイミング、コンポーネントや機能が同じで、分けておく理由のないページはまとめる。

サービス仕様の 1 ページ目は、docv desc と同じ desc.md（assets/desc.md へのシンボリックリンク）にする。docv desc と一致させるため、このページは 1 ファイルのまま保ち、AI Agent が最初に読む要点だけを書く。詳しいことは 2 ページ目以降に書く。

書き分けの例

種類サービス仕様システム仕様
出力HTML のページの作りと、毎回同じ出力にする決まり出力先を作り直し、埋め込んだ CSS と JS を書く流れ
エラーcheck の指摘と終了コード外の道具が見つからないときや、やりとりが途切れたとき
スキーマdocv.yaml の項目スキーマを埋め込み、版のタグの URL で公開すること
外の道具textlint で確かめる項目と、使うかどうかの設定どのコマンドが、どの道具を、いつ呼ぶか

事柄の割り方と持ち主

  • 1 つの事柄も、読者で割って置く
    • 例:「決済サービスの接続文字列は、シークレットから読む」はデプロイする人向けで、ドキュメントに書く
    • 例:「なぜ直接の接続を使うか」はその設定を変える人向けで、その値の隣のコメントに書く
    • サービス仕様とシステム仕様も、利用者に見える結果と、それを出す仕組みで割る（「書き分けの例」）
  • 事柄には、持ち主を 1 つ決める
    • 持ち主は、その事柄を主語にするページか、それを守らせる仕組み（検証器、スキーマ、リンタ、テスト）
    • ほかの場所は、名前で指すだけにし、値や数（「3 段階」「6 本」）を写さない
    • 「〜はテストで確かめる」のような保証の在りかは、保証する側に書く
  • コードのコメントからドキュメントを指すときは、パスや章ではなく、名前で緩く指す

型と形

  • 型（表の列、決まった見出し、「決定 → そのため残ること」）を先に決める
  • 「補足」「注意点」「残るリスク」のような受け皿の節やページを作らない
    • 残るものは、原因になった決定の隣に「そのため、次のことは残る」と書く
  • 直す順は、消す・移す → 型 → 形
    • 文を重ねた箇条書きを子の箇条に割る直しは、情報を減らさず、入れ子だけを増やす
    • 折りたたみや入れ子の崩れは症状で、消せるものを消すと、畳むものはほとんど残らない
  • 読者に置き換えをさせない
    • 環境ごとに変わる値は、表の列にする
    • コマンドは、「変える値の行」と「そのまま貼れるブロック」にする

望ましいドキュメント

  • 概要と詳細が適切に分類されている
    • 概要は要点がまとまっていて、詳細は <details> で折りたたみ必要なときのみ視認できるようになっている（「折りたたみ」の章）
  • 現在の情報が整理されている
  • 用語集の単語に沿って書かれている
  • 事実と予定・課題管理を混ぜない
  • サービス概要とシステム概要が、詳しいページの今の姿を表している
    • 詳しいページに部品や機能を足したら、概要も直す

望ましくないドキュメント

  • mission の示す内容が一意になっていない / ひとつのファイルに複数の内容を混ぜている
  • 過去の情報がすべて羅列されている → 今現在知らなくていいことは随時削除し、必要な経緯は ADR か PDR に移す
  • 作業の報告（やったこと、直したこと、試したこと）が書いてある → 今の姿だけを書き、やったことはコミットメッセージに書く
  • 同じ内容が複数の箇所に書いてある
  • 同じことを言い換えて繰り返している、結論より前置きが長い
  • 実装が書いてあり、コードを変えるたびに直す必要がある
  • Slot のミッションに当たる内容が、Free ファイルに置かれている
  • コードの行番号やドキュメントの章番号など、頻繁に変更される情報に依存している
  • 分岐や合流、多対多のつながりや状態の移り変わりを文や箇条書きで追わせていて、全体の形がつかめない → 図にし、その分の文を消す
    • 上から順に実行する一本道の手順は、箇条書きのままにする
  • 図が今の構成と合っていない、図と同じことを本文でも説明している

折りたたみ

  • 畳んだところを読まなくても、本文だけで話が通るようにする
    • 畳んだところにしか書いていない言葉や決まりを、本文で前提にしない
  • 畳むのは、必要になってから読む詳しいこと（全項目の一覧、例、例外の扱い、理由の細部など）
  • 読む人の誰もが知っておく要点と決まりは、畳まない
  • <summary> を見るだけで、中に何があるかが分かるようにする
  • 作業の報告や古くなった情報など、消すべきものは、畳んで残さずに消す

箇条書き

箇条書きは、項目をざっと拾えるように並べるために使う。句点で文を重ねた項目は、行間の狭い段落と変わらない。

  • 1 項目 1 文にする
    • 2 文以上になるなら、子の項目に分ける
  • 別々の決まりは、別の項目に分ける

参照

  • 本文で ADR と PDR を案内しない
  • ほかの Slot やページの案内は、書かないのを基本にする
    • ページの冒頭に、ほかの Slot やページに何が書いてあるかを並べることだけを禁止し、それ以外は自由にする
    • Slot はミッションで置き場所が分かり、HTML には検索もある

Slot ごとの書き方の目安

Slot目安
API 仕様書、DB 仕様書生成物が正本なら、ページは入口にする。書くのは、開き方、生成の流れ、生成物に載せる範囲と、載せないものの在りか
テスト方針分類ごとに、確かめるものの種類、テストの形（表の軸、期待値の出どころ）、網羅を持つテスト、確かめないことと確かめるところ。ケースはテスト名に任せる
システム概要部品の一覧は図に任せ、主なデータが部品を通る道筋を短く書く
サービス概要まだ地図も言葉も知らない人に向け、用語集の言葉を言い換える

ADR と PDR の作成基準

ADR と PDR は、長く読み返される記録である。今の姿は Slot と Free ファイルに書き、ADR と PDR には、なぜそうなったかを残す。置き場所と章立ては docv desc の「ADR」と「PDR」に従う。

記録残すもの目的
ADR技術の決定なぜその技術や構成を選んだのかを残し、後から変えるときの判断に使う
PDRプロダクトやサービスの仕様の変更（足す、変える、やめる）なぜ今の仕様になったのかを、将来も分かるようにする。仕様を変えるときや、見送った案がまた出たときに、当時の理由と前提を確かめられるように

ADR に書くもの

次のどちらにも当たる技術の決定を書く。

  • 複数の案を比べて選んだ決定で、選んだ理由が今のドキュメントやコードからは読み取れない
  • 長く効き、後から変えるのに手間がかかる
    • 例: 使う言語、IaC の道具、部品の分け方、API の形、データの持ち方

PDR に書くもの

PDR は、仕様がどう変わってきたかの履歴である。案を比べて選んだ決定に限らない。仕様を足す・変える・やめるとき、その理由が今のドキュメントからは読み取れないなら書く。

  • 料金、プラン、提供する機能の範囲、対象とする利用者、サポートの方針などの変更
  • やらないと決めたこと、やめたこと
    • 後から同じ案が出たときに、なぜやらないのかを示せるようにするため

書かないもの

記録書かないこと代わりに書く場所
ADRバグ修正や考慮漏れの手当てなど、今の決定を変えずに直したこと書かない
理由を残したいときはコミットメッセージ
ADR比べた案がなく、理由を残すまでもない決定書かない
両方決定に従って選ぶ細部（関数名、環境変数名、ライブラリの細かな使い方、画面の文言など）書かない
コードから読める
両方移行の計画、進み具合、タスクの一覧、期間を区切った施策など、短い間に状態が変わることdocv/free/plan/

書き方

  • 1 つの記録には、決定か変更を 1 つだけ書く
  • 技術とプロダクトの両方にまたがるときは、仕様の変更を PDR に、それを実現する技術の決定を ADR に分けて書き、「参考」の章で互いにつなぐ
  • その記録だけで読めるように書く
    • 会議や口頭でしか確かめていないことを根拠にしない
    • 根拠は、後から確かめられるファイルや資料へのリンクにし、「参考」の章にまとめる
  • 決めたことは、実装の自由を奪わない粒度で書く
    • 細かさは、「決めたことを守ったまま細部を差し替えたとき、本文を書き換える必要があるか」で確かめる
    • 書き換える必要があるなら、その細部は書かない
  • PDR の見直す条件は、当たったかどうかを後から判断できるように書く
    • 「利用者が増えたら」のような、いつ当たったか分からない書き方をしない
  • 決めた理由を、Issue や PR の番号に預けない
    • 番号だけでは、記録を読んでも理由が分からないため

タグ

Free ファイルにはタグをつけ、ディレクトリを細かく設計せずにタグで分類する。いちばんの目的は、ディレクトリの構造によるドキュメントの管理が破綻しやすいことを避けるため。往々にして複数の属性を持つファイルがあり、ディレクトリで分けると置き場所が定まらない。タグで分類すると、HTML で絞り込んで閲覧しやすくもなる。

タグ書くこと
スキーマdocv.yaml の JSON Schema の写し（docv/free/schema/）

AI Agent への指示

  • セッション開始時に docv desc と docv list を実行し、本ファイルの指示に従いドキュメント管理をすること
  • ドキュメント変更時は docv fix を通すこと
  • ドキュメントを書き足すときは、増えた情報を適切な量で反映すること
  • 実装は、指示がない限り書かないこと
  • 理由や決まりを書く前に、コードとコメントを探し、同じことがあれば写さないこと
  • 一般的な知識は書き写さないこと
  • 手順を書いたら読者としてなぞり、戻せないこと、戻している間の振る舞い、気づけないことが書いてあるかを確かめること
  • 長い手順や注意を書く前に、製品やスクリプトに言わせられないかを人間に提案すること
  • 決まりを変える前に、関わる ADR と PDR を探すこと
  • Free ファイルを足す前に、docv list で、その mission がどれかの Slot のミッションに当たらないかを確かめること
    • 当たるなら、その Slot に書き、長くなるならページに分けること
  • Free ファイルに spec/ や architecture/ のような、Slot の代わりになるディレクトリができそうになったら、Slot のページ（タブ）の分け方を見直すこと
  • 既存の文書を Slot に移すときは、ミッションに当たらない記述を、ほかの Slot、Free ファイル、ADR、PDR に分けること
    • 実装は移さないこと
  • 変わった情報は原則として上書きし、古くなった情報は原則として抹消すること
  • ADR と PDR は加筆の指示があるまで作成せず、「ADR と PDR の作成基準」の書くものに当たる状況では作成提案にとどめること
  • ADR と PDR を書いたら、「ADR と PDR の作成基準」の書かないものと書き方で見直してから、人間へ見せること
  • PDR の見直す条件を満たす状況に気づいたら、その PDR を示して、見直しを提案すること
  • 「望ましくないドキュメント」に当たる記述を、作業中に 2 つ以上のファイルで見つけたら、作業を終えてから、docv review-guide でのレビューを提案すること
  • リリースの前や、大きな機能を入れた後にも、docv review-guide でのレビューを提案すること
  • アスキーアートを用いたいときは、まず SVG で作図すること
  • 画像は docv desc の「画像」の置き方に従い、使うファイルの隣に置くこと
指示の元にした、AI Agent が書くドキュメントの癖
  • 変える人向けの注意を多く書き、使う人の罠を落とす
    • 例: 戻している間はデプロイしても新しい版に切り替わらない、という罠は、手順をなぞらないと出てこない
  • 自分で書いたコードのコメントを、ドキュメントに写す
  • ページの冒頭で、ミッションを言い直す
  • 作業の報告、予定、課題管理の道具の写しを残す
  • 一般的な知識（フレームワークのレビュー観点など）を書き写す
  • 直すよう言われると、形を整える直し（項目を割る、畳む）を選ぶ
