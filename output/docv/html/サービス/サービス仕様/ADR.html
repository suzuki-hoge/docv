概要SlotFreeADRPDR設定ファイルコマンドビジュアライズ

ADR（Architecture Decision Record）は、技術の決定 1 つを、背景、結果、選ばなかった案と一緒に残す記録。Free ファイルと Slot には今の姿だけを書き、どう決めてきたかは ADR と PDR に残す。プロダクトやサービスの決定は PDR に残す。docv が形を決めるファイルの 1 つ。

1. 置き場所と書き方

  • dir.document_root（既定は docv）の下の adr/ に、決定 1 つを 1 つの Markdown で置く。ファイル名は <id>.md で、.md を除いた名前が決定を指す id になる
  • 画像は、adr/ の中に {id}_{画像の名前}.{拡張子} の名前で置き、adr/ の中の画像だけを参照する。外の画像を使いたいときは、写しを置く。決定がそれだけで完結し、ほかのドキュメントを直しても、過去の決定が変わらないようにするため
  • システムが使う項目（group、date、supersedes）は YAML front matter に書く。決定の中身は本文に書き、本文の h1 を題にする
  • 状態（採用、却下など）は持たない。ADR に残すのは決めたことだけで、打ち消されたかどうかは、新しい決定の supersedes から指されているかでわかる。打ち消されていない決定が、今の決定
  • 本文は、決まった章で書く（「本文の章」の章）
  • 決めた後は書き換えない。決定を変えるときは、新しい ADR を書き、その supersedes から過去の決定の id を指す（未来から過去を参照する）
  • 過去の決定から新しい決定へのつながりは、docv が supersedes を逆にたどって組み立てる。過去の ADR には書き足さない
  • 用語を変えても、過去の ADR は書き換えない。過去の ADR が今の用語で読めなくなることは許す。用語集の Slot には今の用語だけを書き、昔の用語との対応は残さない

2. YAML front matter の項目

項目必須中身
group任意まとまりの名前。同じ group の決定を、HTML で 1 つの図にまとめる。省略すると「その他」
date必須決めた日（YYYY-MM-DD）。決定を並べる順と、supersedes が過去を指しているかに使う
supersedes任意打ち消す過去の決定の id の配列

3. 本文の章

本文は、h1 の題の下に、次の章をこの順に h2 で書く。任意の章は、書くことがなければ置かない。

章必須書くこと
背景必須決める必要が生じた課題と、そのときの制約や前提
決めたこと必須決めたことと、その案を選んだ理由。決めたことが当てはまる範囲
決めないこと任意この ADR では決めないことと、それをどこで決めるか
結果必須決めたことで変わること。引き受けること（できなくなること、後で考えること）も書く
選ばなかった案必須比べた案と、それぞれを選ばなかった理由
参考任意根拠にしたファイルや資料へのリンク。ADR だけで読めるように、本文の根拠をここにまとめる
  • 章の形は check で確かめない。章を揃えるのは、ADR を読む人と AI Agent が、どの ADR も同じ順で読めるようにするため
---
group: 言語
date: 2026-03-01
supersedes: [go]
---

# Rust で書く

## 背景

配布するバイナリを 1 つにしたい。利用者の手元に、言語の実行環境を求めたくない。

## 決めたこと

CLI は Rust で書き、単一のバイナリにして配る。CLI の外で動く道具（textlint など）は、この決定の範囲に含めない。

## 決めないこと

バイナリをどこで配るかは決めない。リリースの Slot で決める。

## 結果

利用者は、言語の実行環境なしで使える。開発者は、Rust の環境を用意する。

## 選ばなかった案

| 案             | 選ばなかった理由             |
| -------------- | ---------------------------- |
| Node.js で書く | 利用者の手元に実行環境が要る |
| Zig で書く     | 情報が少ない                 |
