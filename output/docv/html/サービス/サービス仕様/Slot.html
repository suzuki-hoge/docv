どのプロジェクトにも要るドキュメントを、docv が決めたミッションと形で書くファイルの規格。

1. 置き場所と書き方

  • Slot ファイルは、docv.yaml の dir.document_root（既定は docv）の下の slot/ に、<まとまり>/<Slot>.md の名前で置く。まとまりのディレクトリは service（サービス）、system（システム）、guide（開発者向けガイド）、operation（運用）。Free ファイルは free/ に置く（設定ファイル のページの「配置」の章）
  • Slot ファイルは、すべて Markdown（.md）で書き、そのまま HTML に出す
  • サービス仕様、システム仕様、開発コマンド、アーキテクチャ、設計・実装、テスト方針、インフラと環境だけは、ページに分けて <まとまり>/<Slot>/ に置ける（「ページ分け」の章）
  • ADR と PDR は、slot/ ではなく、document_root の下の adr/ と pdr/ に置く
  • slot/ の中でも、除外に当たるファイル（設定ファイル のページの「docv が読むファイル」の章）と、名前がドットで始まるファイルとディレクトリ（.DS_Store など）は読まない。画像（Free のページの「画像」の章）は、Slot の隣に {Slot の名前}_{画像の名前}.{拡張子} の名前で置ける。ページに分けた Slot のページの隣には、{ページの名前}_{画像の名前}.{拡張子} で置ける。それ以外で Slot の名前でないファイルは、check が slot-unknown の error にする
  • Slot を置くかどうかは任意。プロジェクトに当てはまらない Slot は作らない（例: 利用者の手元に入れるものがなければ、インストールの Slot はいらない）
  • Slot のミッションに当たる詳しいことも、Slot の中に書く。Free ファイルへのリンクで済ませない
  • Slot の中のリンクは、ほかの Markdown と同じく、ファイルの場所からの相対パスで書く
  • docv gen <slot> で、Slot ファイルを決まったパスに作れる（docv list で一覧とミッションを出す）

  • アーキテクチャには、部品の分け方とつなぎ方など、システム全体で採る方式と、部品をまたいで守る決まりを書く。どんな部品がありどうつながっているかはシステム概要に、使っている製品やライブラリの名前は技術スタックに書く。たとえば、重い処理をキューに積んでワーカーで非同期に行う方式は、アーキテクチャに書く。そのキューとワーカーはシステム概要に、注文の確定がキューを通ってワーカーに届く流れはシステム仕様に、キューの製品の名前は技術スタックに書く
  • 設計・実装には、コードを書くときに従う決まりを書く。今のコードの作りは書かない。コードを読んでも、守るべき決まりか、たまたまそうなっているかは分からないため。ディレクトリの決まりも、ここに書く
  • テスト方針には、何をどのテストで確かめるかを書く。テストを実行するコマンドは、開発コマンドに書く
  • インフラと環境には、ある環境だけでなく、ない環境も書く（例: ステージングと本番があり、開発サーバーはない）
  • デプロイは環境に反映すること、リリースは利用者に届けることで、どちらかしかないプロジェクトもある（例: サーバーを持たない CLI はリリースだけ）

3. 書き方

  • 中身の形は、check では確かめない
  • YAML front matter には mission を書き、docv list のミッションと同じ文にする。ほかに書けるのは、関わる決定の adr と pdr だけ（Free のページの「関わる決定」の章）。ミッションは docv が決めるもので、プロジェクトでは変えない。ないか違えば、check が slot-mission の error にする。docv の版を上げてミッションが変わったときも、check で気づいて直す。ファイルを開けば、何を書く Slot かが分かるようにするため
  • mission がないか違っても、HTML には本文を出す
  • docv gen は、雛形のある Slot には雛形を作る。ほかの Slot には、YAML front matter の mission だけを書いたファイルを作り、中身の形は自由だと表示する
  • 雛形にも mission を書いてある。作った雛形はプロジェクトのもので、列や文を足すのは自由。docv の版を上げても書き換えない
  • 雛形の形から外れていないかは、check ではなく、docv review-guide のレビューで見る
Slot雛形の形
用語集まとまりごとの h2 の下に、用語、英語、意味の表を置く
技術スタック層ごとの h2 の下に、名前と用途の表を置く
環境変数キー、説明、ローカル環境、運用環境の表を置く。秘密の値のキーには 🔒 を付ける
費用「かかっている費用」と「費用を理由にやっていないこと」の h2 の下に、説明と月額の表を置く。説明は項目の名前から書き出し、参考の URL は末尾に置く

4. ページ分け

サービス仕様、システム仕様、開発コマンド、アーキテクチャ、設計・実装、テスト方針、インフラと環境は、ページに分けられる。1 つのページが長くならないようにするため。読む人ごとに仕様が分かれるサービス（利用者向けの機能と管理者向けの機能など）、部品の多いシステム（画面、サーバ、バッチなど）、部品ごとに開発のコマンドや決まりや環境が違うプロジェクトで分ける。

Slot1 つのファイルページのディレクトリ
サービス仕様service/service.mdservice/service/
システム仕様system/system.mdsystem/system/
開発コマンドguide/develop.mdguide/develop/
アーキテクチャguide/architecture.mdguide/architecture/
設計・実装guide/design.mdguide/design/
テスト方針guide/testing.mdguide/testing/
インフラと環境operation/infrastructure.mdoperation/infrastructure/
  • 分けるときは、1 つのファイルの代わりに、ページのディレクトリの直下に 1 ページ 1 つの Markdown で置く。ファイル名は自由。両方に置くと check の error になる
  • どのページにも、並びの order（整数）とページの名前を書く。ページは order の順に並べる。order もページの名前も、同じ Slot のページどうしで重ねない。ほかの Slot のページとは比べない
  • 分けないときは、今までどおり 1 つのファイルに書く
  • docv gen は、1 つのファイルを作り、分けるときの置き場所も表示する。ページがあるときは、1 つのファイルを作らずに error で終わる。ページは手で置く

ページは、YAML front matter に order と mission を書く。関わる決定の adr と pdr も書ける。mission は、分けないときと同じく、その Slot のミッションと同じ文にする。本文の h1 が、ページの名前になる。
