Review Guide

docv review-guide が出す手順と同じ内容。

AI Agent と開発していると、ドキュメントに作業の報告や経緯、コードの写し、コードを変える人に向けた注意が溜まる。読む人に要らないことが増え、人間がプロジェクトの今の姿をざっと把握しにくくなる。

このレビューの目的は、どのページも、今の姿のうち、そのページの読者に要ることだけを残すこと。

  • 読者に要ることは消さない
    • 量を減らすこと自体は目的にしない
  • 指摘するか迷ったら、直した後に、ページの読者が今の姿をつかみやすくなるかで決める

レビューフロー

docv review-guide の出力を、そのまま AI Agent に渡して使う。

  1. 人間が AI Agent にレビューを頼む
    • 例: 「docv review-guide を実行し、その手順でドキュメントをレビューして」
  2. AI Agent が、調べる範囲を人間に確かめる
  3. AI Agent が「レビュー手順」に沿ってファイルを読み、「報告の形」で指摘を出す
    • ファイルは書き換えない
  4. 人間が、指摘ごとに番号で直し方を選ぶ
    • 直さない指摘には、「このままでいい」と答える
  5. AI Agent が、選ばれた直し方で直す
    • 消す・移す直しを先にし、割る・畳む直しは後にする
    • 直したら、「削るべきでないもの」を消していないかを見直す
    • 最後に、docv fix と docv check を通す

レビュー手順

  1. 調べる範囲を人間に確かめる
    • ドキュメントだけで見るか、コードやインフラの定義も調べるか
    • 頼むときに言われていれば、聞かない
  2. Doc ガイドを読む
    • Doc ガイドがなければ、docv gen doc-guide --print が出す雛形を読む
  3. docv list を実行し、置いた Slot（行の頭に * があるもの）と Free ファイルを、すべて読む
  4. 一覧の ADR と PDR から、題で関わりのあるものを選んで読む
    • ADR と PDR はレビューの対象にせず、書き換えも削除も提案しない
  5. docv_exclude に当たるファイルのうち、Doc ガイドで予定やメモの置き場所にしたものを読む
    • 生成物や、外から持ち込んだ文書の場所は読まない
  6. 「観点」ごとに確かめる
    • 「削るべきでないもの」は削らない
    • 「判断に使わないもの」では判断しない
  7. 「報告の形」で指摘を出す
    • ファイルは、人間が直し方を選ぶまで書き換えない

観点

観点は、docv が守らせるものと、Doc ガイドの基準の 2 つに分かれる。

観点決めるもの変えられるか
今の姿、置き場所と形docv変えられない
Slot のミッションや、docv のディレクトリのルールで決まっている
Doc ガイドと食い違うときは、docv のルールに従う
Doc ガイドの基準プロジェクトDoc ガイドを直せば変わる

今の姿

Slot と Free ファイルには、今の姿だけを、食い違いなく書く。

観点指摘する状態直し方
内容の矛盾同じことを指す記述が、ファイルどうしで食い違っているどちらが今の姿かを調べて、違うほうを直す
分からなければ、両方の記述を示して人間に確かめる
決定との矛盾今の姿として書いたことが、打ち消されていない ADR か PDR の「決めたこと」と食い違っている揃えずに、人間に確かめる
選べるのは、Slot か Free ファイルを直すか、新しい ADR か PDR で決定を打ち消すか
今の姿とのずれ図（SVG）、サービス概要、システム概要が、本文や詳しいページの今の姿と食い違っている。詳しいページに足された部品や機能が抜けている本文や詳しいページに合わせて直す
本文どうしも食い違っていれば、「内容の矛盾」として扱う
作業の報告やったこと、直したこと、試したことが書かれている消す
やったことの置き場所は、Doc ガイドに従う
経緯以前どうだったか、いつ・なぜ変えたか、どの案を比べたかが書かれている。今の決まりを守る理由（「〜のため」）は当たらないADR か PDR に同じ経緯があれば、消す
なければ、消すか、新しい ADR か PDR に移すかを人間に選んでもらう。移す案は、Doc ガイドの、ADR と PDR を書く基準に当たるときだけ出す
予定と課題これからやること、検討中のこと、実装の状態（未実装、止めている）が書かれているDoc ガイドで決めた、予定を置く場所へ移す
足りないもの手順のページを読者としてなぞると、戻せないこと、戻している間の振る舞い、気づけないことが書かれていない書き足さずに、足りないかもしれないことを問いにして人間に出す

置き場所と形

どの Slot に何を書くかは、ミッションで決まっている。1 つのことは 1 か所に書き、Slot は docv の決めた形で書く。

観点指摘する状態直し方
ミッションに合わない記述docv list に出たミッションに合わないことが書かれているミッションに合うファイルへ移す
Slot に書くべき内容が Free にあるSlot のミッションに当たることが、Free ファイルに書かれている。Free ファイルのディレクトリが、Slot の代わりになっているSlot へ移す
内容の重複同じことが、複数のファイルに書かれているミッションに合う 1 か所に残し、ほかは消す
ほかの Slot の案内ページの冒頭で、ほかの Slot やページに何が書いてあるかを説明している（例: 「環境変数は環境変数のページに、テストの実行方法は開発コマンドのページに書く」）消す
どの Slot に何があるかはミッションで分かるので、本文で説明しなくてよい
本文での ADR と PDR の案内Slot や Free ファイルの決まりの文に、ADR や PDR へのリンクや、「理由は ADR に書いた」のような文が付いているYAML front matter の adr か pdr に id を移し、本文から消す
雛形の形から外れている雛形のある Slot（docv gen <slot> --print で出る）が、雛形の見出しや表の形から外れている。列や文を足しただけのものは当たらない雛形の形に合わせる

Doc ガイドの基準

Doc ガイドの基準に合わない記述を、すべて指摘する。章の名前や分け方はプロジェクトごとに違うので、基準の中身から次の種類を決め、その直し方から選ぶ。

基準の種類指摘する状態直し方
書かないものDoc ガイドで書かないとしたもの（一般的な知識、コードを読めば分かることなど）が書かれている消す
ドキュメントの外に置くものDoc ガイドでドキュメントの外に置くとしたものが書かれているDoc ガイドの置き場所へ移す
移す先に同じことがあれば、消す
置き場所Doc ガイドの、どこに書くかの基準（言葉の使い分け、ページの分け方など）に合わない合う Slot、ページ、Free ファイルへ移す
ページを分けるか、まとめる
書き方Doc ガイドの書き方の基準（箇条書き、折りたたみ、図、用語など）に合わない基準に合わせる
読者に要らない文は、合わせる前に消す
そのほか上のどれにも当たらない Doc ガイドの基準に合わない基準に合わせる

削るべきでないもの

削るべきでないもの理由
読者に要る、決まりの理由（「〜のため」）「経緯」の観点で削るのは、以前どうだったかと、なぜ変えたかだけ。今の決まりを守る根拠は、今も効いているので削らない
読者に要る、境目の記述（やらないこと、ないもの、書かないこと）やらないと決めたことや、ないものは、今の姿には現れない。書いておかないと、後から知る方法がない
読者に要る、実装の決まり（コードの分け方や書き方のうち、守らせるために書いたもの）コードを読んでも、守るべき決まりか、たまたまそうなっているかが分からない
概要と詳細の重複概要が詳しいページの要点を持つのは、重複ではない。概要が詳しいページの写しになっているときだけ指摘する
文の中身になっているリンク（正本の置き場所、「〜と同じ」と書いたときの〜など）消すと、文の言っていることが分からなくなる
決まりを書いた文に付けた、根拠や詳しい箇所を章まで指す参照ミッションからは、どの章に書いてあるかまでは分からない
Slot でないもの（Free ファイル、コード、外の資料）への参照置き場所がミッションで決まっていないので、指さないと辿れない
理解を助ける例冗長ではない。本文の流れを切るなら、消さずに畳む
上から順に実行する手順の箇条書き一本道の手順は、図より箇条書きのほうが速く読め、コピーして実行できる

使わないもの理由
行数、ページ数、ファイル数ドキュメントの絶対的な大きさに正解はない
図がないことDoc ガイドの図の基準に当たるときだけ指摘する
置いていない SlotSlot を置くかどうかは、プロジェクトが選ぶ
観点に当たらない書き換え観点に当たらない言い換えは好みの押し付けで、人間の確かめる手間を増やすだけ
Doc ガイドの、AI Agent の作業の進め方の指示書くときの動き方の決まりで、書かれたドキュメントからは確かめられない
docv check で分かることcheck が確かめる
YAML front matter と mission、リンク切れ、見出しの数と章番号、Slot のファイルの名前、太字など
調べる範囲の外のこと範囲は、レビューの初めに人間と決めている
中を読めない画像（PNG、JPG など）の中身読めないものを、推し量って指摘しない
打ち消された ADR と PDR との違い打ち消された決定は履歴で、今の姿ではない
ADR と PDR にあって、Slot と Free ファイルにないこと直すと書き足すことになる

報告の形

指摘のある観点だけを、今の姿、置き場所と形、Doc ガイドの基準の順に出す。指摘のない観点は、最後に「指摘なし: 内容の矛盾、決定との矛盾、…」と 1 行で並べる。当たるものがなければ、無理に探さない。

指摘ごとに、次を書く。

  • 番号、観点、ファイルと箇所
    • Doc ガイドの基準による指摘では、基準を書いた Doc ガイドの箇所も書く
  • 何が問題か
  • 選べる直し方と、それぞれを選んだときの直した後の姿
    • 長ければ要点だけ
    • 「足りないもの」では、直し方の代わりに、人間への問いを書く

書くときの決まりは、次のとおり。

  • 番号は、観点をまたいで 1 から振る通し番号にする
    • 人間と AI Agent が、「3 は消す」のように番号で指摘を指せるようにするため
  • 同じ観点で同じ直し方の指摘が 1 つのファイルに何か所もあるときは、1 つの指摘にまとめ、箇所を並べる
  • 直し方は、観点の表の「直し方」の列にあるものから選ぶ
    • 「人間に確かめる」観点では、確かめたい候補を直し方として並べる（例: A の記述に揃える / B の記述に揃える）
  • ドキュメントのどこにも書いていない情報は、書き足さない
    • 例外は、「決定との矛盾」で新しい ADR か PDR を書くことだけ
  • 選べる直し方には、「何もしない」を入れない
    • 直さないときは、人間が「このままでいい」と答える
  • Doc ガイドの基準による指摘に「このままでいい」と答えたら、その判断を一般化した 1 行を、Doc ガイドに足す案として返す
    • Doc ガイドが変わるので、次のレビューでは同じ指摘が出ない
    • 1 行は当たる範囲を言い切れる書き方にし、基準を丸ごと外す書き方にしない
    • その箇所だけの例外で一般化できなければ、案を返さない
  • 今の姿、置き場所と形の観点による指摘には、Doc ガイドに足す案を返さない
    • Doc ガイドでは変えられないので、その指摘は、次のレビューでも出る
  • 報告の最後に、「直さない指摘には「このままでいい」と答える」と書く
