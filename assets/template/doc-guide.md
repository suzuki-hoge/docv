# Doc ガイド

このプロジェクトのドキュメントを書く・直すときの方針。人間と AI Agent の両方が従う。`docv add doc-guide` が作った雛形で、プロジェクトに合わせて直してよい。

docv の決まりは、ルール、設定、ガイドラインに分かれる（`docv desc` の「ルール、ガイドライン、設定」）。このページは、ガイドラインを書く。

- ルール（Slot と Free ファイルの形、check が確かめること）は、`docv desc` と `docv schema <slot>` で見る
- 設定（`docv.yaml`）は、`docv schema` で見る
- docv の言葉（Slot、Free ファイルなど）は、このプロジェクトのドキュメントに書き写さず、`docv desc` を指す

---

## 1. どこに書くか

まず、書くべき変更かを決める。振る舞い、手順、設定、費用、規約が変わったときだけ書く。コードを変えただけなら、書かないのが正しい。

| 書く内容                                             | 書く場所                                                                                    |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Slot の問いへの答え（`docv add --list` で一覧）      | Slot                                                                                        |
| それ以外の決まったこと                               | Free ファイル。`mission` が問いに合うファイルに書き、なければ作る                           |
| 決めた経緯、選ばなかった案                           | ADR                                                                                         |
| やったこと                                           | PR とコミットメッセージ                                                                     |
| 実装状態、コードの改善点                             | 書かない。必要なら Issue にする                                                             |
| 決めること、確かめていないこと、まとまっていないメモ | 管理外のディレクトリ（`docv.yaml` の `ignore`）。ほかのドキュメントからリンクも言及もしない |

- 同じことを 2 か所に書かない。ほかのファイルにあることは、リンクにする
- Slot の問いに答える詳しいことは、Free ファイルへのリンクで済ませず、Slot に書く。Free ファイルの章を Slot に出すときは、YAML の Slot の `include` で埋め込む
- `README.md` のように YAML front matter を書かないファイルは、管理対象にしない

---

## 2. Slot の書き分け

結果として何が起きるかはサービス仕様に、それをどう実現するかはシステム仕様に書く。

- サービス仕様: 部品ごとに、何を実現するかを書く。振る舞いの決まり（何を対象にし、どの順に処理するかなど）もここに書く。部品の一覧表に「関連する Free ファイル」の列を置き、Free ファイルへのリンクはそこにまとめる
- 利用マニュアル: 使う人から見える振る舞いを、操作ごとに書く
- システム仕様: 外から見えない内部の動きだけを書く。処理の順番、整合性の保ち方、外部サービスの応答や失敗の扱いなど
- デプロイ: 冒頭の 1 文で、何を反映するかを書く
- インフラと環境: 手順を、依存の順に並べる
- ディレクトリ: 役割が分かれる単位（パッケージなど）までを書く。道具の設定のディレクトリ（`.github` など）と、ルートのファイルは書かない

利用マニュアルは、次の形で書く。

- h2 はサービス仕様の部品、h3 は操作の種類（コマンド、画面など）、h4 は操作 1 つにする
- h4 の中身は、コードブロック 1 つと、何をするかの 1〜3 文にする。検査することや止まる条件は、その下に箇条書きで足す
- 複数のコマンドを 1 つのコードブロックに並べ、コメントで説明しない
- エラーの対処表は作らない。対処はエラーメッセージに書き、マニュアルには表示できない対処だけを書く
- 例は 1 つの環境で書き、ほかの環境との違いは冒頭に 1 文で書く

## 3. mission

- このファイルが答えることを、1 文で書く。疑問の形（〜は何か、どう〜か）にすると、範囲が決まる
- ファイルの中身は、`mission` への答えだけにする。AI Agent は `mission` を見て、読むファイルを選ぶ

| 良い                                                         | 悪い                                   |
| ------------------------------------------------------------ | -------------------------------------- |
| 注文の処理は、どの注文をいつ確定し、失敗したときにどう扱うか | 注文の処理について（範囲が決まらない） |

---

## 4. タグ

Free ファイルは、ディレクトリではなくタグで分類する。

| タグ | 書くこと                                     |
| ---- | -------------------------------------------- |
| 仕様 | 振る舞い、データの意味、境界、今の状態の理由 |
| 手順 | コマンド、手順、うまくいかないときの対処     |
| 規約 | コードの書き方など、守ること                 |

どのタグにも、過去の言い回しを警告するルールを付ける。

```yaml
tags: [仕様, 手順, 規約]
lint:
  tags:
    仕様: [no-past-wording]
    手順: [no-past-wording]
    規約: [no-past-wording]
```

## 5. 書き方

今の姿だけを書く。

- 前の内容を直接書き換え、古い内容は消す。後ろに足していかない
- `以前は`、`〜に変更した`、`未実装` のような言い回しを書かない
- 変えた理由を残したいときは、ADR を書く

読む人が受け取れる量にする。

- 本文には要点を書き、細かい理由、例外、例は `<details>` に入れる
- まとめ直しの節（安全装置の一覧表、流れのまとめなど）を作らない。本文と重なり、どちらを直すかが分からなくなる
- 括弧の補足は、1 文に 1 つまでにする
- 表のセルに長い文を入れない。1 行しかない小見出しを作らない。箇条書きの入れ子は浅くする
- 手順の番号 1 つに、条件をいくつも詰め込まない

読む人に分かる言葉で書く。

- 手順の見出しは、何をするかを動詞で書き、コマンド名は括弧で添える。例:「データベースを作る（db-setup）」
- 節の最初の 1 文で、何をするかと、いつ使うかを書く
- 読む人が知らない仕組みの言葉は、初めて出るところで一言説明する
- 部品は、コードの名前ではなく用語集の名前で呼ぶ

範囲を守る。

- 問いに収まらない内容は、別のファイルに書く。内容を収めるために、問いを広げない
- ファイルが大きくなったら、問いを分け、ファイルも分ける

---

## 6. コードとドキュメント

- コード（コメント、エラーメッセージ、テストの名前）から、ドキュメントのパスや章番号を指さない。指すときは、Slot の名前か Free ファイルの h1 で指す。ドキュメントを並べ替えても、コードを直さずに済む
- ドキュメントからコードのパスを指すのはよい
- AI Agent は、ADR を決めた理由を聞かれたときだけ読み、`docv build-html` と `docv build-image` の出力は読まない

---

## 7. 変えたら

- `docv fix` で整形し、`docv check` を通す。空行や表の余白は、手で揃えない
- `docv.yaml` の `output.commit` が true なら、続けて `docv build-html` と `docv build-image` を実行し、出力も同じコミットに入れる
- 書式（章番号、文体、強調など）を決めたら、この章に書き足す。機械で確かめられるものは、`docv.yaml` の `lint` で確かめる
