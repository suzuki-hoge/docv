# レビューガイド

AI Agent と開発していると、ドキュメントに作業の報告や経緯が溜まり、人間がプロジェクトの今の状態をざっと把握しにくくなる。このレビューでは、ドキュメントを蒸留する。今の姿と決まり、その理由、境目（やらないこと）を残す。それらを読み取りやすくする概要や例、参照も残す。それ以外は除く。量を減らすこと自体は目的にしない。指摘するか迷ったら、直した後に人間が今の状態をつかみやすくなるかで決める。

## レビューフロー

`docv review-guide` の出力を、そのまま AI Agent に渡して使う。ファイルを読める AI Agent なら、どれでもよい。

1. 人間が AI Agent にレビューを頼む
   - 例: 「`docv review-guide` を実行し、その手順でドキュメントをレビューして」
2. AI Agent が「レビュー手順」に沿ってファイルを読み、「報告の形」で指摘を出す
   - ファイルは書き換えない
3. 人間が、指摘ごとに番号で直し方を選ぶ
   - 直さない指摘には、「このままでいい」と答える
4. AI Agent が、選ばれた直し方で直す
   - 直したら、「削るべきでないもの」を消していないかを見直し、`docv fix` と `docv check` を通す

## レビュー手順

1. Doc ガイドを読む
   - この手順と Doc ガイドが食い違うときは、Doc ガイドに従う
   - Doc ガイドがなければ、`docv slot gen doc-guide --print` が出す雛形を読む
2. 一覧の Slot ファイルと Free ファイルを、すべて読む
3. 一覧の ADR と PDR から、題で関わりのあるものを選んで読む
   - ADR と PDR はレビューの対象にせず、書き換えも削除も提案しない
4. `docv_exclude` に当たるファイルのうち、メモや予定を置く場所のものを読む
   - 生成物や、外から持ち込んだ文書の場所は読まない
5. 「観点」ごとに確かめる
   - Doc ガイドにあって観点にない基準も確かめ、直し方は観点の表の近いものに合わせる
   - 「削るべきでないもの」は削らない
   - 「判断に使わないもの」では判断しない
6. 「報告の形」で指摘を出す
   - ファイルは、人間が直し方を選ぶまで書き換えない

## 観点

### 中身に関するもの

| 観点 | 指摘する状態 | 直し方 |
| --- | --- | --- |
| 作業の報告 | やったこと、直したこと、試したことが書かれている | 消す。やったことの置き場所は、Doc ガイドに従う |
| 経緯 | 以前どうだったか、いつ・なぜ変えたか、どの案を比べたかが書かれている。今の決まりを守る理由（「〜のため」）は当たらない | ADR か PDR に同じ経緯があれば、Slot や Free ファイルから消す。なければ、消すか、新しい ADR か PDR に移すかを人間に選んでもらう。移す案は、Doc ガイドの「ADR と PDR の作成基準」に当たるときだけ出す |
| 予定と課題 | これからやること、検討中のことが書かれている | `docv_exclude` の領域か Issue へ移す |
| 実装の説明 | コードを読めば分かる局所的なこと（関数やモジュールの分け方、処理の手順）が書かれている。守らせるために書いた決まり（Doc ガイドの「実装の決まり」）と、Doc ガイドで置き場所を決めて書いた実装は当たらない | 消す |
| 内容の矛盾 | 同じことを指す記述が、ファイルどうしで食い違っている | どちらが今の姿かを調べて、違うほうを直す。分からなければ、両方の記述を示して人間に確かめる |
| 決定との矛盾 | 今の姿として書いたことが、打ち消されていない ADR か PDR の「決めたこと」と食い違っている | 揃えずに、人間に確かめる。選べるのは、Slot か Free ファイルを直すか、新しい ADR か PDR で決定を打ち消すか |
| 古い図 | 図（SVG）が、今の構成や本文と食い違っている | 本文に合わせて図を直す。本文どうしも食い違っていれば、「内容の矛盾」として扱う |
| 概要のずれ | サービス概要かシステム概要が、詳しいページの今の姿と食い違っている。詳しいページに足された部品や機能が、概要から抜けている | 詳しいページから要点を持ってきて、概要を置き換える |
| 変わりやすい参照 | コードの行番号やドキュメントの章番号など、すぐに変わるものを頼りに書いている | 見出しの名前やファイルのパスで指すように置き換える |

### 置き場所に関するもの

| 観点 | 指摘する状態 | 直し方 |
| --- | --- | --- |
| ミッションに合わない記述 | 一覧に出したミッションに合わないことが書かれている | ミッションに合うファイルへ移す |
| 内容の重複 | 同じことが、複数のファイルに書かれている | ミッションに合う 1 か所に残し、ほかは消してリンクで指す |
| Slot に書くべき内容が Free にある | Slot のミッションに当たることが、Free ファイルに書かれている。Free ファイルのディレクトリが、Slot の代わりになっている | Slot へ移す |
| 話が混ざったページ | ページに分けられる Slot のファイル（分けていなければそのファイル、分けていれば 1 ページ）に、読み手、読むタイミング、部品や機能の違う話が混ざっている | Doc ガイドの観点で分け、`docv desc` の「ページ分け」の置き方でページにする |
| 分けすぎたページ | 読み手、読むタイミング、部品や機能が同じページや Free ファイルが、分けておく理由もなく分かれている | まとめる |

### 片付けに関するもの

| 観点 | 指摘する状態 | 直し方 |
| --- | --- | --- |
| 解決したメモ | `docv_exclude` の領域に、Slot や Free ファイルにもう反映した決定や、終わった予定が残っている | 消す。解決したと言い切れなければ、人間に確かめる |

### 読みやすさに関するもの

| 観点 | 指摘する状態 | 直し方 |
| --- | --- | --- |
| 冗長 | 同じことを言い換えて繰り返している。結論より前置きが長い | 1 回にまとめ、前置きを消す |
| 文を重ねた箇条書き | 箇条書きの 1 項目に、句点で複数の文が書かれている | 別々の決まりは別の項目に分け、条件や例外、理由は子の項目にする |
| 畳めるのに畳んでいない | 必要になってから読む詳しいこと（全項目の一覧、例、例外の扱い、理由の細部など）が、畳まれずに本文の流れを切っている | 畳む |
| 畳みすぎ | 読む人の誰もが知っておく要点や決まりが、畳まれている。畳んだところを読まないと、本文の話が通らない | 本文に出す |
| 畳んで残した不要物 | 消すべきもの（作業の報告や古くなった情報）が、畳んで残されている | 消す |
| 中身の分からない summary | `<summary>` を見ても、中に何があるかが分からない | `<summary>` を、中身の分かる言葉に置き換える |
| アスキーアート | アスキーアートで図を描いている | SVG に置き換える |
| 図にすべき文 | 分岐、合流、多対多のつながり、状態の移り変わりを、文や箇条書きで追わせていて、全体の形がつかめない | 図に置き換え、その分の文を消す |
| 図と本文の重複 | 図と同じことを、本文でも長く説明している | 本文を消す |
| 用語のゆれ | 同じものを違う言葉で呼んでいる。用語集があるのに、その言葉と違う言葉を使っている | 用語集の言葉に揃える。用語集にない言葉のゆれは、どれに揃えるかを人間に確かめる |

## 削るべきでないもの

| 削るべきでないもの | 理由 |
| --- | --- |
| 決まりの理由（「〜のため」） | 「経緯」の観点で削るのは、以前どうだったかと、なぜ変えたかだけ。今の決まりを守る根拠は、今も効いているので削らない |
| 境目の記述（やらないこと、ないもの、書かないこと） | やらないと決めたことや、ないものは、今の姿には現れない。書いておかないと、後から知る方法がない |
| 実装の決まり（コードの分け方や書き方のうち、守らせるために書いたもの） | コードを読んでも、守るべき決まりか、たまたまそうなっているかが分からない |
| 概要と詳細の重複 | 概要が詳しいページの要点を持つのは、重複ではない。概要が詳しいページの写しになっているときだけ指摘する |
| 別のページへの短い参照（リンクと一言） | 重複ではなく、詳しいことの置き場所を示すもの |
| 理解を助ける例 | 冗長ではない。本文の流れを切るなら、消さずに畳む |
| 上から順に実行する手順の箇条書き | 一本道の手順は、図より箇条書きのほうが速く読め、コピーして実行できる |

## 判断に使わないもの

| 使わないもの | 理由 |
| --- | --- |
| 行数、ページ数、ファイル数 | ドキュメントの絶対的な大きさに正解はない |
| 図がないこと | 図の観点（アスキーアート、図にすべき文など）に当たるときだけ指摘する |
| 置いていない Slot | Slot を置くかどうかは、プロジェクトが選ぶ |
| 観点に当たらない書き換え | 観点に当たらない言い換えは好みの押し付けで、人間の確かめる手間を増やすだけ |
| `docv check` で分かること（YAML front matter と `mission`、リンク切れ、見出しの数と章番号、Slot のファイルの名前とスキーマ、太字など） | check が確かめる |
| コードとドキュメントの矛盾 | このレビューは、ドキュメントを読んで行う。コードは、内容の矛盾を調べるときにだけ読む |
| 中を読めない画像（PNG、JPG など）の中身 | 読めないものを、推し量って指摘しない |
| 打ち消された ADR と PDR との違い | 打ち消された決定は履歴で、今の姿ではない |
| ADR と PDR にあって、Slot と Free ファイルにないこと | 直すと書き足すことになる |

## 報告の形

指摘のある観点だけを、中身、置き場所、片付け、読みやすさの順に出す。指摘のない観点は、最後に「指摘なし: 作業の報告、経緯、…」と 1 行で並べる。当たるものがなければ、無理に探さない。

指摘ごとに、次を書く。

- 番号、観点、ファイルと箇所
- 何が問題か
- 選べる直し方と、それぞれを選んだときの直した後の姿
  - 長ければ要点だけ

書くときの決まりは、次のとおり。

- 番号は、観点をまたいで 1 から振る通し番号にする
  - 人間と AI Agent が、「3 は消す」のように番号で指摘を指せるようにするため
- 同じ観点で同じ直し方の指摘が 1 つのファイルに何か所もあるときは、1 つの指摘にまとめ、箇所を並べる
- 直し方は、観点の表の「直し方」の列にあるものから選ぶ
  - 「人間に確かめる」観点では、確かめたい候補を直し方として並べる（例: A の記述に揃える / B の記述に揃える）
- ドキュメントのどこにも書いていない情報は、書き足さない
  - 例外は、「決定との矛盾」で新しい ADR か PDR を書くことだけ
- 選べる直し方には、「何もしない」を入れない
  - 直さないときは、人間が「このままでいい」と答える
- 「このままでいい」と答えた指摘には、その判断を一般化した 1 行を、Doc ガイドに足す案として返す
  - Doc ガイドが変わるので、次のレビューでは同じ指摘が出ない
  - 1 行は当たる範囲を言い切れる書き方にし、観点を丸ごと外す書き方にしない
- その箇所だけの例外で一般化できなければ、案を返さない
  - その指摘は、次のレビューでも出る
- 報告の最後に、「直さない指摘には「このままでいい」と答える」と書く

## 一覧

Slot、Free ファイル、ADR、PDR には、`docv_exclude` に当たるファイルを含めない。`docv_exclude` の glob は、最後の節に出す。
